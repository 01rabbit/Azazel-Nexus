creates no measurement, admission, activation approval or supported entry.

## Equipment and prerequisites

Use an actual deployment-candidate rugged x86_64 Linux PC, initially the 8 GiB
usable-memory class, with Debian 13 / amd64, LUKS2 storage, recovery passphrase,
and a local console or independent management failsafe. TPM protection is
optional under the [support contract](support-matrix.md). Provide reboot and
power-cycle access, the approved image and exact artifact digests, protected
archive storage outside the checkout, and an independent reviewer.

HG-01/03 need independent capture equipment (second physical recording host
with tap/mirror as applicable). HG-06 needs an isolated test network, a real
decoy namespace/container and controlled responders representing every denied
zone. E2E needs separately approved runtime/model assets and a controlled
remote endpoint only after reserve and provider prerequisites hold. No real
production destination is a test target. No hardware, model, registry, provider
or signer is selected or generated by this preparation.

Install both Nexus distributions **and the Edge Core deployment supplying
azazel-arbiter, azazel-evidence, azazel-leasejournal, azazel-operator and
azazel.slice**. Nexus alone does not supply those; its azazel-auditd is also
required.
Use the read-only `az-hil-readiness` command, linked in
[tools and trust](hil-evidence-records.md#tools-and-trust), to identify missing
units, slice, commissioning key or class. Missing prerequisites block HG-05;
never remove a required subsystem to make the probe run. Initialize the
commissioning key only through the root-only, on-device [procedure](core-reserve-measurement.md#commissioning-key-initialization-root-only); never print or export key material.

## A and B remain separate

Run [hil-preflight](hil-preflight.md) without arguments. Preserve the complete
A-1 through A-11 observations separately from B-1 through B-9 explicit operator
decisions described there and in #115. A includes usable RAM, architecture,
OS/kernel, disk capacity/free space, LUKS/TPM availability, wired/wireless
inventory and connectivity. B includes management/observation roles, every
explicitly unused NIC, external-communication policy, responsible operator,
date, approved anonymous DUT identity, reboot approval and administrative
rights. Unanswered is never interpreted as unused. Connectivity is never role
selection. A ready result authorises no action by itself.

Apply [inventory confidentiality](inventory-confidentiality.md) before writing
anything: raw inventory exists only in the encrypted commissioning record.
Bundle A contains sanitised observations; bundle B contains operator approvals
and workload declarations, not facts invented by the collector. Do not copy
preflight inventory into an issue, ordinary journal or terminal transcript.

## Order at installation and on every boot

1. Before applying any runbook to a particular DUT, require complete A-1–A-11
   and B-1–B-9 through the approved preflight/commissioning path. Missing
   bootstrap support blocks this prerequisite; do not infer missing items.
   Before installation, also obtain explicit approvals for installation,
   disruptive tests and permitted connectivity; establish independent capture
   and console recovery. Run HG-01 on the clean target image **before any
   activation**, then HG-02 while operational units remain masked. Never
   interpret deliberately masked services as a readiness defect to fix here.
2. Run HG-04 and preflight, retaining A/B separately. If the supported bootstrap
   or commissioning promotion path is unavailable, stop that exercise as
   `not-run`/blocked. Do not hand-edit records or manually unmask services to
   manufacture a pass. Installation-state evidence and running-load evidence
   concern different phases and must not be conflated.
3. On **each** subsequent boot, allocate a new run ID and retain the probe v2
   HMAC boot fingerprint and sequence. Recheck the approved image, class,
   inventory continuity, A/B validity, encrypted storage and key availability.
   Use readiness, then HG-07, to establish what is present/running through the
   approved deployment path. Neither step grants activation.
4. Before any observation capability, run HG-03/SO-10 on its commissioned role.
   Before any decoy exposure, run HG-06 on that boot and again before each
   exposure. If either cannot be exercised, keep that capability unavailable.
   An 8 GiB profile need not admit a decoy: record ineligibility, never a pass.
5. For the reserve campaign, have the actual Edge Core subsystems working
   under the declared load. Run HG-05 once per boot, for at least three distinct
   boots per class, without changing harness or class. Keep every run and
   failure; select the maximum of the per-run maxima after attested campaign
   validation. Run SO-01 as ten consecutive cold boots per class under its
   own event/clock rules; sharing boots is allowed only when both procedures'
   conditions hold and evidence explicitly correlates them. Three reserve
   boots do not satisfy ten SO-01 boots.
6. Archive, sanitise, attest and validate each run as specified in
   [evidence records](hil-evidence-records.md). Review the complete campaign
   before consuming a reserve. Re-run affected checks after image, firmware,
   driver, topology, trust or workload changes; retain superseded observations.
7. Only then attempt #100 admission and provider exercises where all remaining
   approval, staged activation and confinement prerequisites are implemented
   and explicitly satisfied. A verified reserve can reach a later refusal; it
   does not implement those gates. Record such refusal and stop dependent
   exercises rather than bypassing it.

## Admission and the six #100 behaviours

On the same declared class, use validated reserve input through the existing
resource gate, then the approved staging-to-promotion and runtime policy paths.
Record artifact generations, trust/lease context, actual admission outcome and
acquisition method. For each scenario, capture healthy baseline, bounded
stimulus, observed route/outcome, durable audit and recovery. Retain failures.

| Exercise | Required observation | What it does not prove |
| --- | --- | --- |
| Local inference | admitted real model returns an inference | model correctness or suitability |
| Remote fallback | induced local failure causes exactly one remote attempt; correlate request and response | arbitrary remote service availability |
| Network loss | remote removed, local answers, deterministic path continues | all network failure modes |
| Model crash | Core continues, model quarantined, restart does not widen rights | all possible crashes |
| Resource pressure | remote, then optional model, then local model shed; capture/evidence/audit/lease expiry retained | capacity beyond this load/class |
| Revocation | in-flight request locally falls back or refuses; revoked route never completes it | revocations outside the exercised timing |

Across baseline, fault and recovery, independently observe unchanged **Edge
arbiter authority, activation lease scope/expiry and enforcement boundary**.
A route label alone proves none of these. Missing observability leaves the
exercise incomplete. No synthetic runtime or simulated response counts as
hardware admission evidence.

## #4 degraded-mode drills

For each admitted CORE/LITE/STANDARD configuration available on the declared
class, use a bounded replay corpus and record healthy baseline, one induced
fault, recovery, then an explicitly declared combined-failure drill. Do not
pretend an unavailable profile ran. Cover local model loss, remote loss,
Knowledge full-node loss, Deception loss, invalid Mission Pack, storage pressure,
service restart/watchdog, stale provider response, topology drift, certificate
revocation and audit-write pressure. Include cold boot, restart and rollback
under the [recovery procedure](recovery.md). Exercise high-RAM but
uncommissioned/topology-ineligible observe-only operation separately from
resource eligibility; this needs its own suitable class, not an inference from
the 8 GiB pilot.

Record usable RAM/class, CPU/storage class facts, protected identity references,
software/assets/generations, quantization, topology, workload and repetitions;
retain latency, RSS, swap, disk growth, queue/backpressure, operator/voice
responsiveness where present, audit continuity, lease expiry/rollback and
restart/recovery observations. Explain each FULL → LITE → CORE capability
transition against effective capability. Demonstrate Core continuation, no
Edge authority widening, and safe re-entry after recovery. This proves only
the exercised faults, timings, hardware/software tuple and load; it does not
establish Pi equivalence, other classes, or general hardware support.

## Stop conditions and review

Stop dependent work on blocked preflight/readiness, missing approvals, missing
protected storage/key, identity drift, class/harness mismatch, unavailable
bootstrap/promotion, lost console/capture, incomplete capture or durable audit,
unexpected packets, unexpected privilege, isolation escape, Core interruption
or lease/enforcement widening. Withdraw affected exposure and follow the
runbook's recovery; never repair evidence in place. Keep classified failures
and incomplete runs. An incomplete exercise cannot yield a passed record.

No VM, Pi, laptop, workstation, CI fixture, shape-only validation or operator
signature alone closes a gate. Field provenance and independent review remain
required. Owner ratification is separate from validator success; only reviewed
hardware evidence can change the gate register or qualify a support entry.
This preparation changes neither.
