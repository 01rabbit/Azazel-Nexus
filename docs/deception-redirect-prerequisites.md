## 1. Problem

[Integration loop §I4](integration-loop.md#i4--redirect-to-deception-lite-later)
(`docs/integration-loop.md:965-998`) names three prerequisites before an Edge
decision can send traffic to a Deception Lite decoy:

1. **Edge enforcement** — the shipped Edge Core is observe-only, so a redirect
   is planned and never applied.
2. **Signed decisions and their key** — Edge signs with a shared HMAC key and
   Nexus has no way to hold it.
3. **A reachable decoy** — Deception Lite listens only on a private Unix
   socket.

Each has a half that belongs to another repository and a half that Nexus has
to design. This proposal covers only the Nexus half. It changes no code and no
authority.

## 3. Prerequisite 1 — Edge enforcement

### Current state

The Edge Core unit Nexus ships has a fixed observe-only environment
(`integration-loop.md:36-42`), and the activation pass grants it only in the
`EDGE_BASELINE` tier. A decision to redirect is shown as "Edge would
redirect". Which Edge component may enforce is the open question of
Azazel-Edge#412.

### What Nexus has to decide

Not *whether to redirect*: that is Edge's, per decision. Nexus decides only
*whether an Edge Core that may enforce is allowed to run on this host*, which
is the same kind of question the activation pass already answers for every
governed unit.

### Options

| option | idea | verdict |
| --- | --- | --- |
| E1 | A **separate enforce-posture Edge unit**, its environment fixed in the unit file, in the existing `ENFORCEMENT` tier. Admission needs everything `EDGE_BASELINE` needs, plus a complete commissioning record whose operator-confirmed scope names the redirect target (`az-decoy0` prefix) and the interfaces Edge may act on, plus the enforce-posture health contract Edge declares. The observe-only unit stays as it is; the two are mutually exclusive in one generation. | **recommended** |
| E2 | Nexus applies the redirect itself (`nft` from a Nexus daemon) when it sees an Edge decision | a second enforcement path, the thing #412 exists to remove; Nexus would become an enforcer; **rejected** |
| E3 | Flip `AZAZEL_DEFENSE_ENFORCE` on the existing unit from a drop-in, environment file or package manifest | an environment switch is a bypass, not a commissioned decision; the manifest is Edge's data and must not choose posture; **rejected** |
| E4 | An operator "allow enforcement" boolean in status or CLI | an approval boolean with no commissioning behind it; **rejected** |
| E5 | Nexus relays Edge's decision back to Edge on a control channel for confirmation | there is no Nexus-to-Edge control channel, by doctrine; **rejected** |

### Why E1 keeps Edge the only decider

The activation pass grants or refuses a *unit*, from evidence, once per boot,
for a later boot. It never sees a traffic decision, never re-derives one and
never vetoes one. What E1 adds is a scope, confirmed by the operator at
commissioning, outside which the enforce-posture unit is not admitted at all.
Inside it, every redirect is Edge's alone. That is the same split as Edge
packaging: Nexus decides whether Edge's binary may run, Edge decides what it
does.

Not in E1: Nexus checking that a particular redirect is inside the scope. That
would be a second, per-decision judgement. The scope is enforced by what the
unit is given (interfaces, target prefix), not by a Nexus check after the
fact.

### Depends on

Azazel-Edge#412 declaring the single path; Edge declaring an enforce posture,
its health contract and how a redirect target is expressed. Until then E1 is
a design only.

## 4. Prerequisite 2 — the decision key

### Current state

The only scheme is Fabric's shared-key HMAC. On a Nexus node, Edge Core (the
signer) and the Nexus consumer (the verifier) run on the same host, under
different accounts.

### Options for the scheme

| | K1: HMAC, shared key (as today) | K2: Ed25519, Edge private key, public key in commissioning |
| --- | --- | --- |
| Fabric change | none | a new signature scheme in `decision_signing` with algorithm and key id fields; Edge producer and AZ-06 consumer follow |
| Who can forge | every reader of the key, including the Nexus verifier | only the holder of the private key (the Edge account) |
| What Nexus stores | a secret, on the LUKS volume, readable by two accounts | a public key, inside the operator-signed commissioning proposal |
| Rotation | new key on both sides at once | new key pair; the public key enters a new commissioning generation |
| Revocation | remove the key; every holder must also forget it | drop the public key from the active record; optionally a revocation role |
| Fits existing Nexus practice | the commissioning binding key (`docs/commissioning.md:275-281`) | the Ed25519 commissioning proposal signature and the key roles of [revocation](revocation.md) |
| Key id / algorithm agility | none in rc5 | part of the change |

Other options considered:

| option | verdict |
| --- | --- |
| K3: no signature; trust the Unix socket peer's credentials (`SO_PEERCRED`) | strong on one host, but leaves no verifiable record after the fact and does not interoperate with the Fabric contract AZ-06 uses; **rejected as the only check, kept as an additional one** |
| K4: key in `Environment=`, an environment file, a unit file, git, an issue, a log or a CI secret | **rejected**; the key would be readable by every reader of those places |
| K5: `systemd-creds` / `LoadCredentialEncrypted=` with the host key | forbidden for commissioning material by the accepted storage design; a decrypt failure stops the unit before it can record a refusal; **rejected** |
| K6: a key generated at build time or shipped in a package | the same key on every node; **rejected** |

### Recommendation

**K2**, proposed to Fabric and Edge as a contract change. The redirect waits
for #412 in any case, so the scheme change does not delay anything that could
otherwise ship. K1 is the fallback only if the Fabric owner declines K2, and
then with every storage rule below and with `SO_PEERCRED` as a second check.

### Lifecycle, at the commissioning level

The rules are the same whichever scheme is chosen; for K2 only the private
half is secret.

- **Generation.** On the node, at commissioning, by an Edge-owned step. Never
  by Nexus build, CI, a test, or another host.
- **Storage.** A fixed path under `/var/lib/azazel/secrets/` on the commissioning
  LUKS device ([#242](https://github.com/01rabbit/Azazel-Nexus/issues/242)):
  root-owned `0700` directory, single-link regular file, size-bounded, opened
  with `O_NOFOLLOW`, the same checks as `commissioning.key`
  (`src/azazel_nexus/commissioning_evidence.py:78-95`). The verifier refuses a
  key directory that is not on a LUKS-backed device. Delivered to the signing
  unit by a plain `LoadCredential=` from that path, not by environment.
- **Binding.** The commissioning proposal records the key's id and, for K2, the
  public key; for K1, only a keyed digest, never the key. A key not bound in
  the active commissioning record is refused.
- **Boot.** A locked volume means no key, so no decision verifies and no decoy
  is materialised by a decision. Edge Core's deterministic path is unaffected.
- **Rotation.** A new key enters through a new commissioning generation and
  approval, as the binding key does. No overlap window: decisions expire in
  minutes (`ttl_seconds=300` by default, `deception_transition.py:117`), so a
  cut-over that refuses for that long is acceptable.
- **Revocation.** Removing the key from the active record. For K2, an optional
  `edge-decision-signing` role in [revocation](revocation.md), which today
  allows exactly two roles; adding one is a change to that design.
- **Verification on every decision.** Signature; `decision_authority ==
  "azazel-edge"`; `target_node_id` is this node; `package_digest` is in the
  verified catalogue generation; inside `[effective_at, expires_at)` on a
  synchronised clock; `decision_id` not seen before (a one-shot ledger,
  persisted, as Edge#358 requires of AZ-06). Any failure refuses the decision
  as a whole and records why, never the key.

### Keeping keys out of places

Never in git, an issue, a PR, a log line, the journal, the audit chain, a
status field, a support bundle or an error message: only a key id and the
refusal code. Test keys are generated per test run in a temporary directory
and never written under `/var/lib/azazel`. A test key cannot become a real one:
production loads only from the fixed path on the LUKS device, and only a key
bound in an operator-approved commissioning record is accepted.

## 5. Prerequisite 3 — a decoy that can be reached

### Current state

Loopback-only by construction (`decoy_loopback.py`), and the static boundary
test forbids internet address families in the runtime. No bridge, no unit, no
exposure path.

### Options

| option | idea | verdict |
| --- | --- | --- |
| D1 | A dedicated network namespace attached to `az-decoy0` by a veth pair. A small one-shot helper unit holds `CAP_NET_ADMIN` only to set up the bridge, the veth pair and the forwarding-deny rules from the commissioning render, inside a namespace that a separate one-shot unit creates (option (a) below); the decoy daemon itself runs in that namespace with no capabilities, its own account, ports ≥ 1024, and the in-code responders of `decoy_loopback.py` | **recommended** |
| D2 | Containers (podman or Docker) on `az-decoy0`, as `IMPLEMENTATION_SPEC.md:805` words it | adds a container runtime, an image store and a runtime socket for responders that are constant byte strings; right for AZ-06 packages, too much for Lite; **deferred** (§7 Q6) |
| D3 | Bind the decoy on a host interface | refused by `decoy.py` already; a general network primitive; **rejected** |
| D4 | Keep loopback and add a host-side proxy from `az-decoy0` | the proxy is a forwarder on the host stack, the path isolation exists to remove; **rejected** |

### D1 in more detail

- **Three one-shot steps, one privilege each (option (a)).** Creating a
  namespace at a fixed path needs a mount, and therefore `CAP_SYS_ADMIN`;
  `CAP_NET_ADMIN` alone cannot do it in practice, and the helper's sandbox
  (`RestrictNamespaces=yes`, `ProtectSystem=strict` with `/run/netns` read
  only, `@system-service` without `mount`) would refuse it anyway. So D1 is
  split into "one unit, one privilege, one act":
  1. a **namespace unit** (one-shot) only creates the decoy namespace at
     `/run/netns/azazel-decoy`. It is expected to be the only unit with
     `CAP_SYS_ADMIN`; its exact privilege is reviewed when it is written;
  2. the **helper** (`CAP_NET_ADMIN`) only configures `az-decoy0`, the veth
     pair into the already created namespace, and the rules;
  3. the **decoy** joins the namespace with no capability.

  The namespace unit is written in the same later phase as the helper's
  body; P1 does not define it. Option (a) is the implementer's choice within
  the accepted design (review of #268, 2026-10-21), not an owner decision;
  the owner may overrule it.
- **Bridge and rules.** `az-decoy0` and its address come only from the
  commissioned bridge prefix (no default). The helper installs forwarding-deny
  rules toward the protected, management, control-plane and Internet zones
  before the decoy unit can start, and removes them only after it stops. Its
  `CAP_NET_ADMIN` is a per-profile bounding set (`hardening.py:179`, as one
  profile already narrows to `CAP_DAC_READ_SEARCH` at `:411`), never ambient
  and never in the decoy daemon. It reads only the commissioning render, never
  a decoy observation or an Edge decision.
- **Isolation check.** A probe runs the denied paths on every boot after the
  helper and before admission, and writes boot-bound, timestamped evidence in
  the three-valued form of `IsolationCheck`. The activation pass consumes only
  fresh evidence from this boot, as the Edge probe of #198 does, and, as for
  every grant, enables the unit for a later boot; the decoy unit's own
  `ExecStartPre=` reruns the probe so that a check exists before every
  exposure (`IMPLEMENTATION_SPEC.md:805`). `None` or `False` keeps the decoy
  unit refused.
- **Decoy unit sandbox.** `SHARED_HARDENING` (`hardening.py:75-100`) with:
  `NetworkNamespacePath=` the decoy namespace; `RestrictAddressFamilies=AF_INET
  AF_INET6 AF_UNIX` (`AF_UNIX` for the observation socket only);
  `IPAddressAllow=` the commissioned prefix and `IPAddressDeny=any`; empty
  capability bounding set; `PrivateUsers=yes`; read-only filesystem except its
  own state directory. It accepts and never initiates: no outbound connect is
  in its code.
- **Runtime boundary test.** A listener module needs a by-file-name exemption
  in `tests/unit/test_runtime_boundary.py:100`. That list is for egress; this
  would be its first ingress entry, and the test should be split so that the
  exemption allows `bind`/`listen` only and still forbids `connect` and
  `create_connection`.
- **Activation.** Add the helper and the decoy unit to `GRANTABLE_UNITS`
  (`activation_markers.py:53`) and to the governed definitions, in a **new tier**
  (proposed name `DECEPTION_EXPOSURE`). It needs: a complete commissioning
  record with the decoy section (bridge prefix, catalogue generation digest);
  this boot's passing isolation evidence; and the masked/preset-disabled
  default every governed unit has. Not `SUPPORTING` (too weak for the one
  feature reachable from outside) and not `ENFORCEMENT` (exposure is not
  enforcement; the `UnitTier` docstring, `activation.py:95-117`, warns against
  letting one readiness condition speak for another).
- **Readiness.** The functional row moves from `loopback-only` to a new word
  only after `HG-06` passes on hardware. A VM run is a mechanics rehearsal.

The observation path does not need enforcement or signed decisions. It needs

## 7. Owner decisions

Recommended defaults in brackets.

1. Which Fabric decision does a Lite decoy consume?
   **[`EnvironmentActivationDecision` to materialise and
   `EnvironmentTerminationDecision` to stop; `EnvironmentTransitionDecision`
   only if Lite gains states beyond on/off]**
2. Decision signature scheme? **[K2, Ed25519, proposed to Fabric with
   algorithm and key-id fields; K1 only if Fabric declines]**
3. Who generates the decision key? **[an Edge-owned step on the node at
   commissioning; never Nexus, never CI]**
4. Decoy runtime for Lite? **[D1: namespace plus veth on `az-decoy0`, no
   container runtime]**
5. Activation tier for the decoy units? **[a new `DECEPTION_EXPOSURE` tier, not
   `SUPPORTING` or `ENFORCEMENT`]**
6. Containers for Lite later? **[not before AZ-06's live gates (Azazel-Edge#358)
   pass; Lite stays on in-code responders]**
7. Allow a listener exemption in the runtime boundary test?
   **[yes, by file name, `bind`/`listen` only, `connect` still forbidden]**
8. May an `EnvironmentEvent` from a decoy carry the peer address?
   **[no; correlate with Edge incidents by decoy and time window only. Raw
   addresses stay out of what Nexus writes, as for Edge's own records]**
9. Enforcement scope in commissioning (E1)? **[operator-confirmed interfaces
   and the `az-decoy0` prefix only; a redirect target outside it means the
   enforce-posture unit is not admitted at all]**
10. Gate bookkeeping? **[`HG-06` stays the bridge gate; one new gate for the
    decoy unit's sandbox on hardware, numbered when added]**

## 8. Invariants

These hold in every phase. A change that needs one relaxed is out of scope.

- **No new decision authority.** Edge decides every redirect, activation and
  termination. Nexus admits units once per boot from evidence and never
  judges, re-derives, vetoes or replays a traffic decision.
- **No bypass.** No approval boolean, environment variable, drop-in, manifest
  field or CLI flag enables enforcement, exposure or redirect. Each is reached
  only through commissioning and the activation pass.
- **No Nexus-to-Edge control channel.** Decoy observations flow into Nexus
  evidence; nothing flows back.
- **A test key never becomes a real one.** Real keys come only from the fixed
  path on the LUKS device and only when bound in an approved commissioning
  record. No key in git, issues, PRs, logs, the journal or status.
- **Fail closed, without touching the deterministic path.** A locked volume,
  missing key, stale isolation evidence, expired or replayed decision refuses
  the decoy; Edge Core continues to detect and decide.
- **A decoy keeps no payload.** Observations record that a decoy was reached,
  never what was sent.
- **A VM run is not hardware evidence.** P3 is a rehearsal; `HG-06` and the
  new gate close only on the real host.

## 9. What this does not establish

Only P1's declarations and boundary (§10) and P2's event and intake path
(§11) are implemented. Nothing here shows
that Edge can express or apply a redirect, that the namespace design isolates
on a real kernel, or that the Fabric or Edge owners accept the K2 change. Each
is a later phase with its own evidence.

## 10. P1 as implemented

The owner adopted every §7 default on 2026-10-21 and chose to start with P1.
P1 defines the units, the tier and the boundary, and **admits nothing**: the
grant condition (this boot's isolation evidence) has no producer yet, so the
tier is withheld on every pass. The evidence producer is deferred to a later
phase rather than built here, because it needs the helper's body (it probes
the denied paths the helper installs), and the helper's body needs the
namespace mechanism decided below.

**Units** (`runtime/src/azazel_nexus_runtime/hardening.py`, rendered by
`tools/render_units.py` into `packaging/systemd/`):

| | `azazel-decoy-netd.service` (helper) | `azazel-decoyd.service` (decoy) |
| --- | --- | --- |
| account | `root`, so that the bounding set reaches it without an ambient grant; `ServiceProfile` allows root only for the controller and this unit | `azdecoy` (new) |
| capabilities | `CapabilityBoundingSet=CAP_NET_ADMIN`, `AmbientCapabilities=` empty; no other unit may declare `CAP_NET_ADMIN` | none |
| address families | `AF_NETLINK` only: it is root, and `AF_UNIX` would reach the service manager over D-Bus | `AF_UNIX AF_INET AF_INET6` (the new `is_decoy_listener` role) |
| network | host namespace (it would configure host links and the veth into the decoy namespace) | `NetworkNamespacePath=/run/netns/azazel-decoy`, `PrivateUsers=yes` |
| addresses | `IPAddressDeny=any` | `IPAddressDeny=any`, no `IPAddressAllow=` |
| writable | nothing | `/var/lib/azazel/decoy` (`azdecoy`, `0700`) |
| type | `oneshot`, `RemainAfterExit=yes` (stopping it stops the decoy first) | `exec`; `Requires=`/`After=` the helper |
| executable | `az-decoy-netd`: refuses, exits 1 | `az-decoyd`: refuses, exits 1 |

Both carry `SHARED_HARDENING`, the three `[Unit]` lines the grant marker
needs (`ConditionPathExists=` on the marker, `Requires=` and `After=` on the
controller), and pass the unit-content and loaded-unit checks of
[activation §8.2](activation-observe-baseline.md#82-unit-content-and-the-loaded-units-251-h-1-m-3).
The installer installs, preset-disables and masks both, like every governed
unit; it never enables or starts them.

**Tier and grant path.** `UnitTier.DECEPTION_EXPOSURE` is new
(`src/azazel_nexus/activation.py`). Both units are in `CORE_UNITS` and in
`activation_markers.GRANTABLE_UNITS`, so every pass checks their files and
loaded definitions. Three things keep them from being granted, each alone
sufficient:

- `ActivationController.activate` takes no isolation evidence, and the tier
  is withheld as `isolation_evidence_absent` whatever else holds;
- `ACTIVATION_UNIT_ALLOWLIST` does not name them, so a policy naming either
  is refused as a whole and no lease holds them; a v2 approval cannot name
  them either (it is limited to `SUPPORTING` and `EDGE_BASELINE`);
- the pass's tripwire narrows everything if either is ever granted.

The pass also checks a decoded policy against its own narrower scope
(`activation_pass.POLICY_UNIT_SCOPE`, the grantable set without the exposure
units), so adding them to `GRANTABLE_UNITS` did not widen what a policy may
name even if the decoder's allowlist were changed.

**Runtime boundary.** `tests/unit/test_runtime_boundary.py` now has two
lists: `EGRESS_EXEMPT` (unchanged) and `LISTENER_EXEMPT = {"decoy_listener.py"}`.
Both are matched by full path (`runtime/src/azazel_nexus_runtime/<name>`), so
a same-named file in a subpackage is not exempt. A listener module may name
`AF_INET`/`AF_INET6` and must bind and listen; it may not name `connect`,
`connect_ex`, `create_connection`, `sendto`, `sendmsg`, `open_connection`,
`sock_connect`, `create_datagram_endpoint`, `socketpair`, `fromfd`, `SOCK_RAW`
or `AF_PACKET`, and a star import from `socket`, `_socket`, `asyncio` or `ssl`
is refused in every module. `decoy_listener.open_listener` binds only a catalogued
`DecoyEntry` address inside the commissioned bridge prefix. Nothing imports
it, and `tests/unit/test_functional_readiness.py` fails the day something
does, so the Deception Lite row stays `loopback-only`.

**Deferred, with what each needs:**

- the namespace unit of option (a) (§5) and the helper's body (`az-decoy0`,
  veth, forwarding-deny rules, their removal on stop), in one phase. The
  namespace unit's privilege (expected: the only `CAP_SYS_ADMIN`) is reviewed
  then; P1's tests pin the helper to exactly `CAP_NET_ADMIN` and `AF_NETLINK`.
  To be handled in that phase as well, from the independent review of #268:
  - m2, the helper's further sandbox: a `SystemCallFilter=` sized to netlink
    work, `ProtectClock=`, `ProtectHostname=`, `ProtectKernelLogs=`,
    `RestrictRealtime=`, and `InaccessiblePaths=` over the D-Bus and systemd

  - n1, the decoy's `Requires=azazel-decoy-netd.service` is not a

    not something the dependency guarantees. To be closed in that phase, for

    decoy conditional on the namespace existing;
  - n2, the decoy combines `PrivateUsers=yes` with `NetworkNamespacePath=`.
    Whether joining (`setns`) a network namespace owned by the initial user
    namespace succeeds in the order systemd actually applies these settings

- **generation measurement before any grant.** The day the tier can be
  granted, the exposure units' files must be in the generation's measured

  granted and not enough once they may be;
- **HG-02 records.** The HG-02 record validator expects every non-root
  governed daemon exactly once. A record captured before P1 has no `azdecoy`
  attempt and no longer conforms; HG-02 is to be captured afresh. The root

- the per-boot isolation probe, its boot-bound evidence and the activation
  pass consuming it (only then can the tier be granted);
- how the commissioned bridge prefix reaches the decoy's `IPAddressAllow=`:
  not a drop-in, which #253 refuses on every grantable unit;
- the decoy daemon (responders, and sending P2's `EnvironmentEvent`s, whose
  shape and intake path §11 implements) and the decoy's `ExecStartPre=` probe
  rerun;
- `docs/IMPLEMENTATION_SPEC.md` §4 (near line 604) named `azazel-enforced` as
  the only daemon with `CAP_NET_ADMIN`; this PR corrects that sentence to
  name the decoy network helper as the one other holder.

Unit tests only. No `nft` or `ip` is run, no namespace is created and no real

## 11. P2 as implemented

Implemented in #269. P2 builds the event, its validation and the intake's
path for it, with unit tests and one end-to-end step. The decoy daemon that
would send it is still a later phase (§10), so in a real deployment nothing
sends one yet.

**The event** (`src/azazel_nexus/decoy_interaction.py`). A Fabric
`EnvironmentEvent` (`environment-event/v0.1`, Azazel-Fabric `v0.9.0rc5`),
narrower than Fabric's model. A decoy is the one Nexus component an attacker
talks to, so the sender is given **no field it may fill freely**: every
identifier is an exact match with a value the intake knows, or is replaced by
the intake. (The first revision of #269 checked formats only; its review
found a decimal or hex IPv4, a colonless IPv6 and a host name passing them.)

| field | value |
| --- | --- |
| `event_type` | `interaction`, nothing else |
| `event_id` | checked for its form (`evt-` and 32 lower-case hex digits), then **replaced by the intake** with its own random id; what the decoy sent is not stored. A meaningless random value |
| `environment_id` | exactly one of `DECOY_NAMES` (`ssh-decoy`, `smtp-decoy`, `http-decoy`, `telnet-decoy`), fixed in code until the catalogue reaches the intake |
| `package_id` | exactly `azazel-nexus/deception-lite`: a Lite decoy is an in-code responder, not an AZ-06 package |
| `node_id` | exactly the intake's node id, `local` until the commissioned node identity reaches the intake |
| `observed_at` | whole seconds in UTC (`…T12:00:00Z`), within 300 s of the intake's clock on arrival (`DECOY_CLOCK` otherwise) |
| `evidence_refs` | always `[]` |
| `metadata` | exactly `bytes_received` (0–4096, the decoy's read ceiling), `truncated` (only at that ceiling) and `responder` (one of the four in-code responders) |

Anything else is refused as a whole with a fixed code (`DECOY_SHAPE`,
`DECOY_TYPE`, `DECOY_RANGE`, `DECOY_CLOCK`, `DECOY_JSON`, `DECOY_TOO_LARGE`),
never with the input: an extra or missing field, a value outside its set, a
line over 1 KiB. An address-like spelling (an IP address, dotted or dashed
IPv4, colon-separated hex, a MAC address) is also refused as `DECOY_ADDRESS`,
as a second check; the guarantee of §7 Q8 rests on the exact matches, not on
that pattern. The values that passed the first revision are pinned in
`tests/unit/test_decoy_interaction_p2.py` (`REVIEW_BYPASSES`).

What a sender can still choose is a name among four, a responder among four,
a byte count, a flag and a second within a ten-minute window: about thirty
bits per event, at 30 events a minute. That is a bounded side channel for
whoever holds the `azdecoy` account, not room for a payload, a credential or
an address. Two bindings are left to the phase that wires the catalogue and
the node identity into the intake, and are recorded here rather than
pretended: the catalogue generation digest is **not** in the event (an
unchecked digest would be 256 bits the sender chooses), and `node_id` is a
constant, not the commissioned identity.

Fabric is not imported; a reference test validates the shape with the
pinned Fabric when it is installed. The decoy builds its event from its own
`Observation`, which has no payload and no peer field
(`runtime/src/azazel_nexus_runtime/decoy_report.py`).

**The intake's entry** (`runtime/src/azazel_nexus_runtime/edge_intaked.py`).
The intake binds a second socket, `/var/lib/azazel/run/decoy-intake/decoy-intake.sock`,
in a leaf of its own (`2710 azintake:azdecoy`, socket `0660`), so the decoy is
never given Edge's socket and Edge never reaches this one. No new group: the
leaf uses the decoy account's own group from P1. The intake unit gains
`ReadWritePaths=-/var/lib/azazel/run/decoy-intake`, because it binds the
socket there; the `-` keeps a node whose leaf does not exist yet (a runtime
upgraded without re-running `install.sh`) from failing the whole intake at
namespace setup (226/NAMESPACE). The decoy unit needs no change: connecting
to a socket needs no write access to the read-only tree, as for Edge Core and
its intake socket.

- **Sender.** `SO_PEERCRED`; only the `azdecoy` uid is accepted
  (`decoy_peer_refused` otherwise). Nothing is ever written back.
- **Bounds.** At most 4 decoy readers, which never take one of Edge's 64; 16
  accepts per batch; the read deadline Edge has; one line per connection; 30
  interactions per rolling minute (`decoy_rate_limited` beyond). The rate is
  applied before a record is queued, so a decoy cannot fill the queue Edge
  uses; an interaction the full queue turns away (`decoy_overloaded`) takes no
  place in the minute. An accept error on the decoy socket (`EMFILE`,
  `ECONNABORTED`, …) is counted as `decoy_accept_error` and ends that batch;
  it never reaches Edge's loop.
- **Refusals** are counted in the intake's status and written to a bounded
  refusal log (#230: per uid and reason, rotated by size) at
  `/var/lib/azazel/edge-intake/decoy-refusals.jsonl`: uid and code only.
- **Optional.** Without the `azdecoy` account the socket is not opened; if
  its leaf or storage is unusable, `decoy_listener_unavailable` is counted.
  A failure to store one interaction is `decoy_storage_failed` and never
  latches Edge's `storage_failed`. Either way Edge's intake runs as before.

**Storage.** Interactions go to `/var/lib/azazel/edge-intake/decoy-evidence/`,
daily segments beside Edge's `evidence/`, never in it, with their own ceilings
(8 MiB a day, 64 MiB retained), so a decoy flood cannot fill Edge's evidence
day. Each record is labelled: `kind: nexus.deception-lite.interaction`,
`observer: azazel-nexus`, `edge_observation: false`, then the event, its
digest and the intake's receive time. An Edge record keeps its schema
(`event`, `digest`, `received_at`) and has none of those fields. A decoy
record is never counted in `accepted` or `processed` (Edge's counts), never
reaches the incident tracker and so never opens, updates or closes an
incident, and never reaches the explainer, M.I.O. or the audit chain.

**What the ceilings do not protect.** There is no deduplication and no
sampling. A decoy that floods (or whoever holds its account) can use the
whole minute's allowance and, at about 600 bytes a record, the day's 8 MiB:
later genuine interactions that day are then refused
(`decoy_rate_limited`, `decoy_evidence_segment_full`) and only counted. The
damage stays inside the decoy's own evidence: Edge's evidence, queue places,
reader slots, incidents and status counts are untouched.

**Status.** It gains an optional `decoy` object (`accepted`,
`last_accepted_at`) while the decoy socket is open, and new refusal codes.
`read_intake_status` in this build accepts snapshots with or without them. A
reader from before this change has a closed key and code list and would take
such a snapshot as unreadable (`None`) as a whole; the reader and the writer
ship in the same distribution, so this matters only for a reader copied out
of it. The follow-up checked this from the readers' side: the only readers of
the snapshot in the distribution are `read_intake_status`, the `edge loop:`
section of `azazel-nexus status` built on it, and `tools/e2e_loop.py`; a unit
test (`test_every_reader_in_the_package_accepts_the_decoy_key`) feeds each the
intake's own snapshot with and without `decoy` and with every decoy refusal
code counted.

**Shown in status** (follow-up to #269). `azazel-nexus status` ends the
intake's part of `edge loop:` with one line:
`decoy (Deception Lite; Nexus's own observation, not Edge's; not hardware evidence): accepted N; last accepted Ns ago; refused M (CODE=n, …)`,
or `decoy (Deception Lite): not listening (decoy socket not open); refused M`.
Only the counts, the last time and refusal counts per fixed code; no address,
payload or stored interaction. The decoy's refusal codes
(`DECOY_REFUSAL_CODES`) moved from the intake's `refusals:` to this line, so
they are not read as Edge's. Status stays read-only and gained no permission.

**Joining an incident.** `decoy_interaction.incidents_near` names the Edge
incidents an interaction may belong to by decoy and time only (§7 Q8): the
incident's target port is the decoy's catalogued port, and the interaction
arrived within a window (300 s by default) of the incident's first to last
sighting, both on the intake's clock. It reads; it changes no incident and
feeds nothing to Edge. No reader calls it yet.

**Not done in P2:** the decoy daemon and its sender; showing decoy
interactions in an explanation; a VM run (P3). (Status shows their counts
since the follow-up above.)
`tools/e2e_loop.py` sends one interaction as `azdecoy` in the integrated loop
and checks that it is stored apart and that Edge's evidence, counts and
incidents are unchanged; that is a container run, not VM or hardware
evidence.

## 12. The decoy body as implemented

The decoy daemon deferred in §10 and §11. `az-decoyd`
(`runtime/src/azazel_nexus_runtime/decoyd.py`) now listens, answers and
reports. It still **admits nothing**: the unit is never granted in this
build (the `DECEPTION_EXPOSURE` tier is withheld as
`isolation_evidence_absent`, §10), so on a node nothing starts it. The unit
profile (`hardening.py`) is unchanged; its rationale still says the
executable refuses and exits, and is corrected with the namespace unit's
phase, which owns that file.

**Where it may listen** (`decoy_netns.py`). It binds the IPv4 wildcard of
the network namespace it runs in, which in the host namespace would be every
host interface, so it refuses (exit 1, no socket made) unless its own
namespace (`/proc/self/ns/net`) is the same nsfs inode as
`/run/netns/azazel-decoy` and, when PID 1's namespace is readable, not PID
1's. Under `PrivateUsers=yes` and its own account PID 1's usually is not
readable, and the positive match stands alone; only root can create that
path. The check runs at start and again before every bind. The paths are
constants; there is no argument, environment variable or flag that skips it.

**What it serves** (`SERVED`, fixed in code like the responders, because the
catalogue does not reach the decoy yet): `ssh-decoy` on 2222, `telnet-decoy`
on 2323 and `http-decoy` on 8080, three being the ceiling in every envelope
(`MAX_DECOYS`). The SMTP responder stays in the table without a port. Each
connection gets its responder's constant banner from `decoy_loopback.py`,
then the decoy counts what arrives into one scratch buffer, zeroed after each
read, up to 4096 bytes or 5 s, and closes. Nothing received is stored,
logged or forwarded. Only IPv4 is bound.

**Bounds.** One thread and one selector (the unit has `TasksMax=16`). At most
8 open connections; at most 30 served connections per rolling minute (the
intake's own decoy rate, a test keeps them equal); 5 s per connection.
A connection over a bound is accepted and closed at once, unanswered and
unreported, and only counted (`dropped_busy`, `dropped_rate`).

**What it reports.** Each served connection becomes P2's closed event
(`decoy_report.interaction_from_observation`), sent as one line to
`/var/lib/azazel/run/decoy-intake/decoy-intake.sock` by `decoy_sender.py`
with a 0.5 s deadline. Nothing is read back. If the intake is absent, full
or slow, the interaction is dropped and counted (`send_failed`); the decoy
keeps serving. The peer address `accept` returns is discarded at the call;
the event has no field for it (§7 Q8); the log carries only ports and
counts.

**The runtime boundary, and the one connect.** The listener rule of §7 Q7
(`decoy_listener.py` may bind and listen, never connect) is unchanged. The
report needs one `AF_UNIX` connect, which the listener rule forbids. Rather
than loosen that rule, `tests/unit/test_runtime_boundary.py` now applies it
to **every** module the decoy process loads (`DECOY_PROCESS`, the import
closure of `decoyd.py`, checked to be exactly six files), with one
exception, `DECOY_SENDER = "decoy_sender.py"`, matched by full path. The
sender may name `connect` and nothing else the listener may not; it may not
name an internet or datagram family, `bind`, `listen` or `accept`; its only
family is `AF_UNIX` stream; it has exactly one `connect(_PATH)`; `_PATH` is
assigned once, from `DECOY_INTAKE_SOCKET`, and that is a literal equal to
the layout's decoy-intake socket. No module of the decoy process may name
`environ`, `getenv` or a process call. Twenty-one mutations of the real
files (an internet or datagram family, another path, a second connect,
`sendto`, an environment read, a new import of an egress module, a connect
in the listener or the daemon) are each caught, and so is a same-named
sender in a subpackage. The sender has no `AF_INET` exemption: it gains nothing from
`EGRESS_EXEMPT` or `LISTENER_EXEMPT`.

`decoy_listener.open_namespace_listener` sets one socket option,
`SO_REUSEADDR`, so that a restart is not refused while a closed connection is
in `TIME_WAIT`; the P1 test that read the listener's calls now allows exactly
that one. The functional-readiness row stays `loopback-only`: its test now
allows exactly one importer of the listener, `decoyd.py`, whose unit is never
granted.

**Deferred:** the decoy's `ExecStartPre=` probe rerun; the catalogue and the
commissioned prefix reaching the decoy (and then binding the catalogued
address, `open_listener`, instead of the namespace wildcard); IPv6; the
`IPAddressAllow=` question of §10. A loopback run in a container is not VM
or hardware evidence; `HG-06` and the decoy-sandbox gate stay open.
