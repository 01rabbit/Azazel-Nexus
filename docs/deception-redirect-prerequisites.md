## 1. Problem

[Integration loop §I4](integration-loop.md#i4--redirect-to-deception-lite-later)
(`docs/integration-loop.md:965-998`) names three prerequisites before an Edge
decision can send traffic to a Deception Lite decoy:

1. **Edge enforcement** — the shipped Edge Core is observe-only, so a redirect
   is planned and never applied.
2. **Signed decisions and their key** — Edge signs with a shared HMAC key and
   Nexus has no way to hold it.
3. **A reachable decoy** — Deception Lite listens only on a private Unix
   socket.

Each has a half that belongs to another repository and a half that Nexus has
to design. This proposal covers only the Nexus half. It changes no code and no
authority.

## 3. Prerequisite 1 — Edge enforcement

### Current state

The Edge Core unit Nexus ships has a fixed observe-only environment
(`integration-loop.md:36-42`), and the activation pass grants it only in the
`EDGE_BASELINE` tier. A decision to redirect is shown as "Edge would
redirect". Which Edge component may enforce is the open question of
Azazel-Edge#412.

### What Nexus has to decide

Not *whether to redirect*: that is Edge's, per decision. Nexus decides only
*whether an Edge Core that may enforce is allowed to run on this host*, which
is the same kind of question the activation pass already answers for every
governed unit.

### Options

| option | idea | verdict |
| --- | --- | --- |
| E1 | A **separate enforce-posture Edge unit**, its environment fixed in the unit file, in the existing `ENFORCEMENT` tier. Admission needs everything `EDGE_BASELINE` needs, plus a complete commissioning record whose operator-confirmed scope names the redirect target (`az-decoy0` prefix) and the interfaces Edge may act on, plus the enforce-posture health contract Edge declares. The observe-only unit stays as it is; the two are mutually exclusive in one generation. | **recommended** |
| E2 | Nexus applies the redirect itself (`nft` from a Nexus daemon) when it sees an Edge decision | a second enforcement path, the thing #412 exists to remove; Nexus would become an enforcer; **rejected** |
| E3 | Flip `AZAZEL_DEFENSE_ENFORCE` on the existing unit from a drop-in, environment file or package manifest | an environment switch is a bypass, not a commissioned decision; the manifest is Edge's data and must not choose posture; **rejected** |
| E4 | An operator "allow enforcement" boolean in status or CLI | an approval boolean with no commissioning behind it; **rejected** |
| E5 | Nexus relays Edge's decision back to Edge on a control channel for confirmation | there is no Nexus-to-Edge control channel, by doctrine; **rejected** |

### Why E1 keeps Edge the only decider

The activation pass grants or refuses a *unit*, from evidence, once per boot,
for a later boot. It never sees a traffic decision, never re-derives one and
never vetoes one. What E1 adds is a scope, confirmed by the operator at
commissioning, outside which the enforce-posture unit is not admitted at all.
Inside it, every redirect is Edge's alone. That is the same split as Edge
packaging: Nexus decides whether Edge's binary may run, Edge decides what it
does.

Not in E1: Nexus checking that a particular redirect is inside the scope. That
would be a second, per-decision judgement. The scope is enforced by what the
unit is given (interfaces, target prefix), not by a Nexus check after the
fact.

### Depends on

Azazel-Edge#412 declaring the single path; Edge declaring an enforce posture,
its health contract and how a redirect target is expressed. Until then E1 is
a design only.

## 4. Prerequisite 2 — the decision key

### Current state

The only scheme is Fabric's shared-key HMAC. On a Nexus node, Edge Core (the
signer) and the Nexus consumer (the verifier) run on the same host, under
different accounts.

### Options for the scheme

| | K1: HMAC, shared key (as today) | K2: Ed25519, Edge private key, public key in commissioning |
| --- | --- | --- |
| Fabric change | none | a new signature scheme in `decision_signing` with algorithm and key id fields; Edge producer and AZ-06 consumer follow |
| Who can forge | every reader of the key, including the Nexus verifier | only the holder of the private key (the Edge account) |
| What Nexus stores | a secret, on the LUKS volume, readable by two accounts | a public key, inside the operator-signed commissioning proposal |
| Rotation | new key on both sides at once | new key pair; the public key enters a new commissioning generation |
| Revocation | remove the key; every holder must also forget it | drop the public key from the active record; optionally a revocation role |
| Fits existing Nexus practice | the commissioning binding key (`docs/commissioning.md:275-281`) | the Ed25519 commissioning proposal signature and the key roles of [revocation](revocation.md) |
| Key id / algorithm agility | none in rc5 | part of the change |

Other options considered:

| option | verdict |
| --- | --- |
| K3: no signature; trust the Unix socket peer's credentials (`SO_PEERCRED`) | strong on one host, but leaves no verifiable record after the fact and does not interoperate with the Fabric contract AZ-06 uses; **rejected as the only check, kept as an additional one** |
| K4: key in `Environment=`, an environment file, a unit file, git, an issue, a log or a CI secret | **rejected**; the key would be readable by every reader of those places |
| K5: `systemd-creds` / `LoadCredentialEncrypted=` with the host key | forbidden for commissioning material by the accepted storage design; a decrypt failure stops the unit before it can record a refusal; **rejected** |
| K6: a key generated at build time or shipped in a package | the same key on every node; **rejected** |

### Recommendation

**K2**, proposed to Fabric and Edge as a contract change. The redirect waits
for #412 in any case, so the scheme change does not delay anything that could
otherwise ship. K1 is the fallback only if the Fabric owner declines K2, and
then with every storage rule below and with `SO_PEERCRED` as a second check.

### Lifecycle, at the commissioning level

The rules are the same whichever scheme is chosen; for K2 only the private
half is secret.

- **Generation.** On the node, at commissioning, by an Edge-owned step. Never
  by Nexus build, CI, a test, or another host.
- **Storage.** A fixed path under `/var/lib/azazel/secrets/` on the commissioning
  LUKS device ([#242](https://github.com/01rabbit/Azazel-Nexus/issues/242)):
  root-owned `0700` directory, single-link regular file, size-bounded, opened
  with `O_NOFOLLOW`, the same checks as `commissioning.key`
  (`src/azazel_nexus/commissioning_evidence.py:78-95`). The verifier refuses a
  key directory that is not on a LUKS-backed device. Delivered to the signing
  unit by a plain `LoadCredential=` from that path, not by environment.
- **Binding.** The commissioning proposal records the key's id and, for K2, the
  public key; for K1, only a keyed digest, never the key. A key not bound in
  the active commissioning record is refused.
- **Boot.** A locked volume means no key, so no decision verifies and no decoy
  is materialised by a decision. Edge Core's deterministic path is unaffected.
- **Rotation.** A new key enters through a new commissioning generation and
  approval, as the binding key does. No overlap window: decisions expire in
  minutes (`ttl_seconds=300` by default, `deception_transition.py:117`), so a
  cut-over that refuses for that long is acceptable.
- **Revocation.** Removing the key from the active record. For K2, an optional
  `edge-decision-signing` role in [revocation](revocation.md), which today
  allows exactly two roles; adding one is a change to that design.
- **Verification on every decision.** Signature; `decision_authority ==
  "azazel-edge"`; `target_node_id` is this node; `package_digest` is in the
  verified catalogue generation; inside `[effective_at, expires_at)` on a
  synchronised clock; `decision_id` not seen before (a one-shot ledger,
  persisted, as Edge#358 requires of AZ-06). Any failure refuses the decision
  as a whole and records why, never the key.

### Keeping keys out of places

Never in git, an issue, a PR, a log line, the journal, the audit chain, a
status field, a support bundle or an error message: only a key id and the
refusal code. Test keys are generated per test run in a temporary directory
and never written under `/var/lib/azazel`. A test key cannot become a real one:
production loads only from the fixed path on the LUKS device, and only a key
bound in an operator-approved commissioning record is accepted.

## 5. Prerequisite 3 — a decoy that can be reached

### Current state

Loopback-only by construction (`decoy_loopback.py`), and the static boundary
test forbids internet address families in the runtime. No bridge, no unit, no
exposure path.

### Options

| option | idea | verdict |
| --- | --- | --- |
| D1 | A dedicated network namespace attached to `az-decoy0` by a veth pair. A small one-shot helper unit holds `CAP_NET_ADMIN` only to set up the bridge, the veth pair and the forwarding-deny rules from the commissioning render, inside a namespace that a separate one-shot unit creates (option (a) below); the decoy daemon itself runs in that namespace with no capabilities, its own account, ports ≥ 1024, and the in-code responders of `decoy_loopback.py` | **recommended** |
| D2 | Containers (podman or Docker) on `az-decoy0`, as `IMPLEMENTATION_SPEC.md:805` words it | adds a container runtime, an image store and a runtime socket for responders that are constant byte strings; right for AZ-06 packages, too much for Lite; **deferred** (§7 Q6) |
| D3 | Bind the decoy on a host interface | refused by `decoy.py` already; a general network primitive; **rejected** |
| D4 | Keep loopback and add a host-side proxy from `az-decoy0` | the proxy is a forwarder on the host stack, the path isolation exists to remove; **rejected** |

### D1 in more detail

- **Three one-shot steps, one privilege each (option (a)).** Creating a
  namespace at a fixed path needs a mount, and therefore `CAP_SYS_ADMIN`;
  `CAP_NET_ADMIN` alone cannot do it in practice, and the helper's sandbox
  (`RestrictNamespaces=yes`, `ProtectSystem=strict` with `/run/netns` read
  only, `@system-service` without `mount`) would refuse it anyway. So D1 is
  split into "one unit, one privilege, one act":
  1. a **namespace unit** (one-shot, `azazel-decoy-nsd.service`) only
     creates the decoy namespace at `/run/netns/azazel-decoy`. It is the
     only unit with `CAP_SYS_ADMIN`, and the only one without the shared
     file-system sandbox (a mount namespace would keep the handle from the
     host, VM-checked); its exact privilege is in §10. *As implemented
     (§13):* it does more than create the namespace. It also creates the
     veth pair with the decoy's end inside, and configures the inside (`lo`,
     the address, the route), so it holds `CAP_NET_ADMIN` as well;
  2. the **helper** (`CAP_NET_ADMIN`) only configures `az-decoy0`, the veth
     pair into the already created namespace, and the rules;
  3. the **decoy** joins the namespace with no capability.

  The namespace unit's profile, tier membership and boundary were added
  after P1 (§10, "The namespace unit"); its body comes in the same later
  phase as the helper's. Option (a) is the implementer's choice within the
  accepted design (review of #268, 2026-10-21), not an owner decision; the
  owner may overrule it.
- **Bridge and rules.** `az-decoy0` and its address come only from the
  commissioned bridge prefix (no default). The helper installs forwarding-deny
  rules toward the protected, management, control-plane and Internet zones
  before the decoy unit can start, and removes them only after it stops. Its
  `CAP_NET_ADMIN` is a per-profile bounding set (`hardening.py:179`, as one
  profile already narrows to `CAP_DAC_READ_SEARCH` at `:411`), never ambient
  and never in the decoy daemon. It reads only the commissioning render, never
  a decoy observation or an Edge decision. *As implemented (§13):* the
  commissioning render does not reach it yet. Its commands, names and
  addresses are constants, and the only output it reads is its own
  read-back of the table and links (§14).
- **Isolation check.** A probe runs the denied paths on every boot after the
  helper and before admission, and writes boot-bound, timestamped evidence in
  the three-valued form of `IsolationCheck`. The activation pass consumes only
  fresh evidence from this boot, as the Edge probe of #198 does, and, as for
  every grant, enables the unit for a later boot; the decoy unit's own
  `ExecStartPre=` reruns the probe so that a check exists before every
  exposure (`IMPLEMENTATION_SPEC.md:805`). `None` or `False` keeps the decoy
  unit refused. *As implemented (§14):* the pass runs before the three units,
  so it can never hold this boot's evidence; the evidence is instead a record
  the helper writes after building and the decoy requires before it listens,
  and the tier stays withheld.
- **Decoy unit sandbox.** `SHARED_HARDENING` (`hardening.py:75-100`) with:
  `NetworkNamespacePath=` the decoy namespace; `RestrictAddressFamilies=AF_INET
  AF_INET6 AF_UNIX` (`AF_UNIX` for the observation socket only);
  `IPAddressAllow=` the commissioned prefix and `IPAddressDeny=any`; empty
  capability bounding set; `PrivateUsers=yes`; read-only filesystem except its
  own state directory. It accepts and never initiates a network connection:
  no outbound network connect is in its code. *As implemented (§12):* it has
  one `AF_UNIX` connect, `decoy_sender`'s report to the intake's decoy
  socket.
- **Runtime boundary test.** A listener module needs a by-file-name exemption
  in `tests/unit/test_runtime_boundary.py:100`. That list is for egress; this
  would be its first ingress entry, and the test should be split so that the
  exemption allows `bind`/`listen` only and still forbids `connect` and
  `create_connection`.
- **Activation.** Add the namespace unit, the helper and the decoy unit to `GRANTABLE_UNITS`
  (`activation_markers.py:53`) and to the governed definitions, in a **new tier**
  (proposed name `DECEPTION_EXPOSURE`). It needs: a complete commissioning
  record with the decoy section (bridge prefix, catalogue generation digest);
  this boot's passing isolation evidence; and the masked/preset-disabled
  default every governed unit has. The three are granted together or not
  at all (§10). Not `SUPPORTING` (too weak for the one
  feature reachable from outside) and not `ENFORCEMENT` (exposure is not
  enforcement; the `UnitTier` docstring, `activation.py:95-117`, warns against
  letting one readiness condition speak for another).
- **Readiness.** The functional row moves from `loopback-only` to a new word
  only after `HG-06` passes on hardware. A VM run is a mechanics rehearsal.

## 8. Invariants

These hold in every phase. A change that needs one relaxed is out of scope.

- **No new decision authority.** Edge decides every redirect, activation and
  termination. Nexus admits units once per boot from evidence and never
  judges, re-derives, vetoes or replays a traffic decision.
- **No bypass.** No approval boolean, environment variable, drop-in, manifest
  field or CLI flag enables enforcement, exposure or redirect. Each is reached
  only through commissioning and the activation pass.
- **No Nexus-to-Edge control channel.** Decoy observations flow into Nexus
  evidence; nothing flows back.
- **A test key never becomes a real one.** Real keys come only from the fixed
  path on the LUKS device and only when bound in an approved commissioning
  record. No key in git, issues, PRs, logs, the journal or status.
- **Fail closed, without touching the deterministic path.** A locked volume,
  missing key, stale isolation evidence, expired or replayed decision refuses
  the decoy; Edge Core continues to detect and decide.
- **A decoy keeps no payload.** Observations record that a decoy was reached,
  never what was sent.
- **A VM run is not hardware evidence.** P3 is a rehearsal; `HG-06` and the
  new gate close only on the real host.

## 9. What this does not establish

Only P1's declarations and boundary, the namespace unit's declaration
(§10), P2's event and intake path (§11), the decoy's body (§12), the
bodies of the namespace unit and the helper (§13) and the per-boot isolation
evidence (§14) are implemented, and none of the three units is ever granted. Nothing here shows
that Edge can express or apply a redirect, that the namespace design isolates
on a real kernel, or that the Fabric or Edge owners accept the K2 change. Each
is a later phase with its own evidence.

Two limits of what is implemented, recorded by the review of #276 (F6):

- **The namespace unit is contained only by its body.** It is root with
  `CAP_SYS_ADMIN`, `CAP_NET_ADMIN`, the `mount` system call and no
  file-system sandbox (§10). Its bounding set, system call filter,
  `RestrictNamespaces=net mnt` and netlink as its only family narrow what it
  is handed but do not stop a compromised body from acting as host root.
  The netlink family cannot be narrowed to a protocol, so it can also change
  nftables. In practice its containment is the body being fixed (constant
  commands, no input) and a mandatory access control (LSM) profile that does
  not exist yet.
- **The single-writer premise no longer holds.** Before #196 the only root
  process that could write the activation state (unmask, enable, grant
  markers) was `az-activated`. The namespace unit is a second root process
  with no file-system sandbox, so a compromised body could write that state
  too. The helper is root as well, though its sandbox is narrower. HG-02 as
  written does not cover either unit, because its runbook never runs as
  root.

Both are inside what the design accepted, as long as none of the three units
is granted. **Grant condition:** before the `DECEPTION_EXPOSURE` tier may be
granted, an LSM profile confining the namespace unit (and the helper) must
exist and be a gate. That means a hardware-gate record showing that, under
the profile, the unit cannot write the activation state, the grant markers
or the unit files, and cannot reach the service manager.

The profiles now exist (#196 G3,
[grant design §7](deception-exposure-grant.md#g3-as-implemented)): each of
the three units names its own with `AppArmorProfile=` and no `-`, and the
pass's enforce-mode check is defined. That is not the gate: the
hardware-gate record does not exist, the check is not yet a grant
condition, and the tier is still withheld on every pass.

## 10. P1 as implemented

The owner adopted every §7 default on 2026-10-21 and chose to start with P1.
P1 defines the units, the tier and the boundary, and **admits nothing**: the
grant condition (this boot's isolation evidence) has no producer yet, so the
tier is withheld on every pass. The evidence producer is deferred to a later
phase rather than built here, because it needs the helper's body (it probes
the denied paths the helper installs), and the helper's body needs the
namespace mechanism decided below.

**Units** (`runtime/src/azazel_nexus_runtime/hardening.py`, rendered by
`tools/render_units.py` into `packaging/systemd/`):

**Tier and grant path.** `UnitTier.DECEPTION_EXPOSURE` is new
(`src/azazel_nexus/activation.py`). Both units are in `CORE_UNITS` and in
`activation_markers.GRANTABLE_UNITS`, so every pass checks their files and
loaded definitions. Those checks are not limited to the tier: if any of the
three units' vendor file or loaded definition departs from the rendered one
in any way (a drop-in, an edited file, a definition loaded from elsewhere),
the `systemd_loaded_units` producer fails and **the whole pass is refused**.
No unit is granted that boot, Edge Core and every supporting unit included.
Three units that are never granted can therefore veto the product's own
activation. That fails closed, but it needs care in operation; see
[operations](operations.md#deception-lite-decoy-network-196). A typical
cause is a VM check that unmasks the units by hand and removes the marker
condition or the controller dependency with a drop-in, then leaves it in
place. Separately, the library layer that performs unit calls,
`systemd_bus.SystemdUnitCalls`, accepts every unit in the fixed unit table
(`units.UNIT_NAMES`), the three included, for `UnmaskUnitFiles` and
`EnableUnitFiles`. What keeps them masked is the controller, which never
names them (below), not that layer. Three things keep them from being
granted, each alone sufficient:

- `ActivationController.activate` takes no isolation evidence, and the tier
  is withheld as `isolation_evidence_absent` whatever else holds;
- `ACTIVATION_UNIT_ALLOWLIST` does not name them, so a policy naming either
  is refused as a whole and no lease holds them; a v2 approval cannot name
  them either (it is limited to `SUPPORTING` and `EDGE_BASELINE`);
- the pass's tripwire narrows everything if either is ever granted.

The pass also checks a decoded policy against its own narrower scope
(`activation_pass.POLICY_UNIT_SCOPE`, the grantable set without the exposure
units), so adding them to `GRANTABLE_UNITS` did not widen what a policy may
name even if the decoder's allowlist were changed.

**Why it has no file-system sandbox.** systemd runs a unit with any of those
settings in a mount namespace of its own, and cuts propagation from it to the
host. The bind mount that makes a named network namespace is then never seen
outside the unit (n3). Leaving them out loses nothing real: a process with
`CAP_SYS_ADMIN` and the `mount` system call could unmount or remount any of
them inside its own mount namespace, so for this unit they were never a wall.

**A compromised body is host root.** Root with `CAP_SYS_ADMIN` and `mount`
can mount a fresh `/proc` or `/sys` and rewrite `kernel.core_pattern` and
the like, or remount the cgroup file system read-write; no unit setting
stops that. The bounding set, the system call filter,
`RestrictNamespaces=net mnt`, netlink as its only family (every netlink
protocol, nftables included) and `NoNewPrivileges=` narrow what it is
handed, and nothing more. Its containment rests on the
body itself: fixed in code, taking no input (no argument, file, environment
or socket), statically reviewed, and later confined by a mandatory access
control (LSM) profile. To be weighed in the body phase: **removing the
privilege instead**, by letting systemd hold the namespace. For example,
the helper and the decoy share one network namespace through
`PrivateNetwork=yes` and `JoinsNamespaceOf=`, and the helper moves one veth
end to the host; then no unit needs `CAP_SYS_ADMIN` and the namespace unit
goes away. Whether that ordering and lifetime work is itself a VM item.

`ServiceProfile` pins this unit whole: its capability, account, families,
the absence of any writable path, its own settings, the two shared overrides,
the seven shared omissions, its executable, its ordering (`After=` and
`Requires=` the controller only, nothing else) and its single grant-marker
condition must be exactly these. No other unit may override or leave out any
`SHARED_HARDENING` entry, nor restate in its free-form `extra` a shared key,
`User=`, `CapabilityBoundingSet=`, `AmbientCapabilities=`,
`SystemCallFilter=`, `RestrictAddressFamilies=`, `ReadWritePaths=`,
`BindPaths=` or `InaccessiblePaths=` (each comes only from a declared field
or the shared set); a test checks that every other packaged unit carries the
whole mount sandbox. It carries the
three marker lines (`ConditionPathExists=` on its marker, `Requires=` and
`After=` on the controller), and passes the unit-content and loaded-unit
checks of
[activation §8.2](activation-observe-baseline.md#82-unit-content-and-the-loaded-units-251-h-1-m-3).
It is in `CORE_UNITS` (tier `DECEPTION_EXPOSURE`), `GRANTABLE_UNITS`, the
tripwire and the unit table (`decoy-namespace`), never in
`ACTIVATION_UNIT_ALLOWLIST` or a v2 approval. The installer installs,
preset-disables and masks it; it never enables or starts it.

**The body** is in §13. The VM-checked configuration ran
`ExecStart=/usr/sbin/ip netns add <name>` and `ExecStop=/usr/sbin/ip netns
delete <name>`; the body runs the same two acts first and last, through its
fixed executable, and configures the inside in between.

The chain is namespace unit → helper → decoy: the helper has `After=` and
`Requires=` on the namespace unit, the decoy on the helper.

**The tier is granted together or not at all** (closes n1 below). systemd
counts a unit skipped for an unmet `ConditionPathExists=` (no grant marker)
as a success for the units that `Requires=` it, so a dependency alone does
not keep the decoy from starting without the helper, or the helper without
the namespace unit. The rule is held in three places, each alone sufficient:

- `ActivationController` refuses a governed set that holds some but not all
  of `DECEPTION_EXPOSURE_UNITS`, holds one of them in another tier, or gives
  one of them a wiring requirement;
- a lease whose unit scope names some but not all of them withholds the
  ones it names as `exposure_tier_partial` (the others are
  `outside_lease_scope`). Every other precondition is the same for the three
  (none has a wiring, the evidence check is per tier), so their verdicts
  cannot otherwise differ; a test pins that they are identical;
- `activation_markers.write_grant_markers` refuses a marker set holding some
  but not all of them (`EXPOSURE_UNITS`, compared with the library's tuple
  by a test). This is also the backstop for the one difference the library
  cannot rule out in advance: an unmask that fails for one of the three
  after the others were granted.

None of this grants anything: the tier is still withheld as
`isolation_evidence_absent` on every pass, no policy can name the three, and
the tripwire narrows everything if any one of them, or all three, is ever
granted.

**Before any grant: what the tier still needs** (review of #276, F1 and F2).
In addition to the items above, the generation measurement, the approved
prefixes, the `HG-06` and decoy-sandbox gates and the LSM gate of §9, the
tier is not granted until each of the following is designed, implemented
and tested:

- **A table removed after start is not detected (F1).** The helper reads the
  table back once, when it starts (§14). After that, nothing notices if the
  `inet azazel_decoy` table is removed or replaced. On Debian,
  `nftables.service` loads `/etc/nftables.conf` on start and reload, and the
  default file begins with `flush ruleset`; its stop runs
  `nft flush ruleset`. Each removes every table, this one included. An Edge Core in
  the enforce posture that replaces the ruleset would do the same. The
  helper stays `active` (`RemainAfterExit=yes`), its record still reads
  `pass`, and the decoy keeps listening with no table in front of it. Today
  `approved_v4` is empty and nothing is granted, so nothing is exposed, but
  a grant would make this an exposure.

  **Done: the boot order against `nftables.service`.** The helper carries
  `After=nftables.service` (`hardening.HOST_FIREWALL_UNIT`), and only that:
  no `Requires=`, `Wants=`, `BindsTo=` or `PartOf=`, so a host without the
  unit or with it failed is not affected, and `After=` on a unit that does
  not exist is a no-op. Debian's unit is `DefaultDependencies=no` and only
  `WantedBy=sysinit.target`, with no `Before=` on `sysinit.target` or
  `basic.target`, so the helper's default dependencies did not order it
  after the firewall load; at boot the `flush ruleset` could run after the
  table was loaded and checked. The decoy is ordered after the helper, so it
  follows the firewall too. No `Before=` is needed: the helper has to come
  later, and a `Before=nftables.service` would bring the race back. At
  shutdown the order reverses, so the helper's stop removes its table before
  the firewall's stop flushes the ruleset. `ServiceProfile` pins the
  helper's ordering whole, and the file still passes the #253 content check
  and the loaded-unit check (both require the controller lines, not the
  absence of others). In a systemd 257.13 container (a mechanism check with
  stand-in units, not hardware evidence): started in one transaction, the
  firewall's start finished before the helper's; with no `nftables.service`
  the helper started and the unit read `LoadState=not-found`.

  **Still open, and still before any grant.** Ordering only orders jobs that
  are queued together. In the same container, with the helper active,
  `reload`, `stop`, `start` and `restart` of `nftables.service` each ran
  its command and the helper stayed `active`: `After=` propagates neither a
  stop nor a reload (that would take `PartOf=`, `PropagatesReloadTo=` or
  similar, which would hand the firewall a say over the decoy units). So
  the following still remove the table unnoticed, and the design must state
  how each is handled:
  - **a later reload, stop, restart or start of the firewall**, by the
    operator, a package upgrade or anything else;
  - **Edge's enforce.** The helper has no ordering on Edge's enforce unit,
    and an Edge Core that replaces the ruleset removes the table whenever it
    does so;
  - **any other flush**: `firewalld`, `iptables-nft` restore, or a manual
    `nft flush ruleset`;
  - **coexistence with the host's firewall management.** Which of these may
    run on a decoy host, and how each leaves `inet azazel_decoy` alone. For
    example, a commissioning check that refuses a host whose
    `/etc/nftables.conf` flushes the whole ruleset, or an agreed
    `destroy table` scope instead of `flush ruleset`;
  - **a read-back on every decoy start.** §14 leaves this to the grant
    phase. A decoy restarted later in the boot must not rely on the record
    taken when the helper started;
  - **monitoring while running.** For example, a periodic fixed read-back
    by a privileged unit, with any departure stopping the three units (stop
    of the namespace unit). Or an `nft monitor` style watch whose only
    action is that stop. Either has to be fixed in code, take no input and
    have no switch that disables it. This is designed with the grant phase.

  Until then, operations tells the operator to stop the three units when
  the table is gone.
- **Q9 changes five fixed places at once (F2).** Approved prefixes (§7 Q9)
  cannot be added without changing each of the following, and each change
  is a design decision of its own, not an implementation detail:
  1. `decoy_network.NFT_RULESET`: today a constant whose set `approved_v4`
     is empty. Adding elements means either a ruleset built from data, or a
     second command that adds elements;
  2. `decoy_isolation_check.EXPECTED_NFT_LISTING` and the check
     `approved_v4_empty`. Both pin an empty set exactly, so they would have
     to compare against the approved prefixes instead, and `nft_table` would

  3. `decoy_network._ALLOWED`: every argument list the helper may run is a
     constant today, and `run_fixed` refuses any other. A prefix in an
     argument list ends that;
  4. the decoy's `IPAddressAllow=`: stated statically in the profile (one
     allowance, `10.255.196.0/30`, pinned by `ServiceProfile`) because #253
     refuses drop-ins. Approved prefixes need either a rendered unit per
     commissioning or a new way to deliver an allowance;
  5. the generation the operator signs: the exposure units' files and the

     (`measure_scoped_unit_files`), so that the prefixes the helper loads are
     the ones the operator approved.

  Together these mean **the helper takes input** for the first time. Its

## 11. P2 as implemented

Implemented in #269. P2 builds the event, its validation and the intake's
path for it, with unit tests and one end-to-end step. The decoy daemon that
would send it is still a later phase (§10), so in a real deployment nothing
sends one yet.

**The event** (`src/azazel_nexus/decoy_interaction.py`). A Fabric
`EnvironmentEvent` (`environment-event/v0.1`, Azazel-Fabric `v0.9.0rc5`),
narrower than Fabric's model. A decoy is the one Nexus component an attacker
talks to, so the sender is given **no field it may fill freely**: every
identifier is an exact match with a value the intake knows, or is replaced by
the intake. (The first revision of #269 checked formats only; its review
found a decimal or hex IPv4, a colonless IPv6 and a host name passing them.)

| field | value |
| --- | --- |
| `event_type` | `interaction`, nothing else |
| `event_id` | checked for its form (`evt-` and 32 lower-case hex digits), then **replaced by the intake** with its own random id; what the decoy sent is not stored. A meaningless random value |
| `environment_id` | exactly one of `DECOY_NAMES` (`ssh-decoy`, `smtp-decoy`, `http-decoy`, `telnet-decoy`), fixed in code until the catalogue reaches the intake |
| `package_id` | exactly `azazel-nexus/deception-lite`: a Lite decoy is an in-code responder, not an AZ-06 package |
| `node_id` | exactly the intake's node id, `local` until the commissioned node identity reaches the intake |
| `observed_at` | whole seconds in UTC (`…T12:00:00Z`), within 300 s of the intake's clock on arrival (`DECOY_CLOCK` otherwise) |
| `evidence_refs` | always `[]` |
| `metadata` | exactly `bytes_received` (0–4096, the decoy's read ceiling), `truncated` (only at that ceiling) and `responder` (one of the four in-code responders) |

Anything else is refused as a whole with a fixed code (`DECOY_SHAPE`,
`DECOY_TYPE`, `DECOY_RANGE`, `DECOY_CLOCK`, `DECOY_JSON`, `DECOY_TOO_LARGE`),
never with the input: an extra or missing field, a value outside its set, a
line over 1 KiB. An address-like spelling (an IP address, dotted or dashed
IPv4, colon-separated hex, a MAC address) is also refused as `DECOY_ADDRESS`,
as a second check; the guarantee of §7 Q8 rests on the exact matches, not on
that pattern. The values that passed the first revision are pinned in
`tests/unit/test_decoy_interaction_p2.py` (`REVIEW_BYPASSES`).

What a sender can still choose is a name among four, a responder among four,
a byte count, a flag and a second within a ten-minute window: about thirty
bits per event, at 30 events a minute. That is a bounded side channel for
whoever holds the `azdecoy` account, not room for a payload, a credential or
an address. Two bindings are left to the phase that wires the catalogue and
the node identity into the intake, and are recorded here rather than
pretended: the catalogue generation digest is **not** in the event (an
unchecked digest would be 256 bits the sender chooses), and `node_id` is a
constant, not the commissioned identity.

Fabric is not imported; a reference test validates the shape with the
pinned Fabric when it is installed. The decoy builds its event from its own
`Observation`, which has no payload and no peer field
(`runtime/src/azazel_nexus_runtime/decoy_report.py`).

**The intake's entry** (`runtime/src/azazel_nexus_runtime/edge_intaked.py`).
The intake binds a second socket, `/var/lib/azazel/run/decoy-intake/decoy-intake.sock`,
in a leaf of its own (`2710 azintake:azdecoy`, socket `0660`), so the decoy is
never given Edge's socket and Edge never reaches this one. No new group: the
leaf uses the decoy account's own group from P1. The intake unit gains
`ReadWritePaths=-/var/lib/azazel/run/decoy-intake`, because it binds the
socket there; the `-` keeps a node whose leaf does not exist yet (a runtime
upgraded without re-running `install.sh`) from failing the whole intake at
namespace setup (226/NAMESPACE). The decoy unit needs no change: connecting
to a socket needs no write access to the read-only tree, as for Edge Core and
its intake socket.

- **Sender.** `SO_PEERCRED`; only the `azdecoy` uid is accepted
  (`decoy_peer_refused` otherwise). Nothing is ever written back.
- **Bounds.** At most 4 decoy readers, which never take one of Edge's 64; 16
  accepts per batch; the read deadline Edge has; one line per connection; 30
  interactions per rolling minute (`decoy_rate_limited` beyond). The rate is
  applied before a record is queued, so a decoy cannot fill the queue Edge
  uses; an interaction the full queue turns away (`decoy_overloaded`) takes no
  place in the minute. An accept error on the decoy socket (`EMFILE`,
  `ECONNABORTED`, …) is counted as `decoy_accept_error` and ends that batch;
  it never reaches Edge's loop.
- **Refusals** are counted in the intake's status and written to a bounded
  refusal log (#230: per uid and reason, rotated by size) at
  `/var/lib/azazel/edge-intake/decoy-refusals.jsonl`: uid and code only.
- **Optional.** Without the `azdecoy` account the socket is not opened; if
  its leaf or storage is unusable, `decoy_listener_unavailable` is counted.
  A failure to store one interaction is `decoy_storage_failed` and never
  latches Edge's `storage_failed`. Either way Edge's intake runs as before.

**Storage.** Interactions go to `/var/lib/azazel/edge-intake/decoy-evidence/`,
daily segments beside Edge's `evidence/`, never in it, with their own ceilings
(8 MiB a day, 64 MiB retained), so a decoy flood cannot fill Edge's evidence
day. Each record is labelled: `kind: nexus.deception-lite.interaction`,
`observer: azazel-nexus`, `edge_observation: false`, then the event, its
digest and the intake's receive time. An Edge record keeps its schema
(`event`, `digest`, `received_at`) and has none of those fields. A decoy
record is never counted in `accepted` or `processed` (Edge's counts), never
reaches the incident tracker and so never opens, updates or closes an
incident, and never reaches the explainer, M.I.O. or the audit chain.

**What the ceilings do not protect.** There is no deduplication and no
sampling. A decoy that floods (or whoever holds its account) can use the
whole minute's allowance and, at about 600 bytes a record, the day's 8 MiB:
later genuine interactions that day are then refused
(`decoy_rate_limited`, `decoy_evidence_segment_full`) and only counted. The
damage stays inside the decoy's own evidence: Edge's evidence, queue places,
reader slots, incidents and status counts are untouched.

**Status.** It gains an optional `decoy` object (`accepted`,
`last_accepted_at`) while the decoy socket is open, and new refusal codes.
`read_intake_status` in this build accepts snapshots with or without them. A
reader from before this change has a closed key and code list and would take
such a snapshot as unreadable (`None`) as a whole; the reader and the writer
ship in the same distribution, so this matters only for a reader copied out
of it. The follow-up checked this from the readers' side: the only readers of
the snapshot in the distribution are `read_intake_status`, the `edge loop:`
section of `azazel-nexus status` built on it, and `tools/e2e_loop.py`; a unit
test (`test_every_reader_in_the_package_accepts_the_decoy_key`) feeds each the
intake's own snapshot with and without `decoy` and with every decoy refusal
code counted.

**Shown in status** (follow-up to #269). `azazel-nexus status` ends the
intake's part of `edge loop:` with one line:
`decoy (Deception Lite; Nexus's own observation, not Edge's; not hardware evidence): accepted N; last accepted Ns ago; refused M (CODE=n, …)`,
or `decoy (Deception Lite): not listening (decoy socket not open); refused M`.
Only the counts, the last time and refusal counts per fixed code; no address,
payload or stored interaction. The decoy's refusal codes
(`DECOY_REFUSAL_CODES`) moved from the intake's `refusals:` to this line, so
they are not read as Edge's. Status stays read-only and gained no permission.

**Joining an incident.** `decoy_interaction.incidents_near` names the Edge
incidents an interaction may belong to by decoy and time only (§7 Q8): the
incident's target port is the decoy's catalogued port, and the interaction
arrived within a window (300 s by default) of the incident's first to last
sighting, both on the intake's clock. It reads; it changes no incident and
feeds nothing to Edge. No reader calls it yet.

**Not done in P2:** the decoy daemon and its sender; showing decoy
interactions in an explanation; a VM run (P3). (Status shows their counts
since the follow-up above.)
`tools/e2e_loop.py` sends one interaction as `azdecoy` in the integrated loop
and checks that it is stored apart and that Edge's evidence, counts and
incidents are unchanged; that is a container run, not VM or hardware
evidence.

## 12. The decoy body as implemented

The decoy daemon deferred in §10 and §11. `az-decoyd`
(`runtime/src/azazel_nexus_runtime/decoyd.py`) now listens, answers and
reports. It still **admits nothing**: the unit is never granted in this
build (the `DECEPTION_EXPOSURE` tier is withheld as
`isolation_evidence_absent`, §10), so on a node nothing starts it. This
phase left the unit profile (`hardening.py`) as it was. The phase that wrote
the namespace unit's and the helper's bodies (§13) then changed it: it added
`IPAddressAllow=10.255.196.0/30` and brought the rationale up to date (it
no longer says the executable refuses and exits).

**Where it may listen** (`decoy_netns.py`). It binds the IPv4 wildcard of
the network namespace it runs in, which in the host namespace would be every
host interface, so it refuses (exit 1, no socket made) unless all three
hold:

1. its own namespace (`/proc/self/ns/net`) is the same nsfs inode as
   `/run/netns/azazel-decoy`;
2. when PID 1's namespace is readable, it is not PID 1's (under
   `PrivateUsers=yes` and its own account it usually is not readable);
3. the interfaces of **its own** namespace, read from `/proc/self/net/dev`
   (which the kernel answers for the reader's namespace), are `lo` and at
   most the decoy's end of the veth pair, `DECOY_VETH = "az-decoy-ns0"`,
   and nothing else.

The third check is independent of the first two. Without it, a path at
`/run/netns/azazel-decoy` that named the host's namespace, with PID 1's
unreadable, would have passed on the inode match alone (review of #272); a
host namespace has a physical or bridge interface and is refused. A fresh
decoy namespace has `lo` alone (as a VM run of the namespace unit showed),
and the veth end is allowed for when the helper's body moves it in; the
helper must use that name, which is fixed here. `/sys/class/net` is not
used: it shows the namespace sysfs was mounted in. A kernel that creates
its fallback tunnel devices (`sit0`, `tunl0`, ...) in every new namespace is
refused as well; such a host sets `net.core.fb_tunnels_only_for_init_net`.
That is a refusal to start, never a listener in the wrong place. The
refusal counts the extra interfaces and never names them. The check runs at
start and again before every bind. The paths are constants; there is no
argument, environment variable or flag that skips it.

**What it serves** (`SERVED`, fixed in code like the responders, because the
catalogue does not reach the decoy yet): `ssh-decoy` on 2222, `telnet-decoy`
on 2323 and `http-decoy` on 8080, three being the ceiling in every envelope
(`MAX_DECOYS`). The SMTP responder stays in the table without a port. Each
connection gets its responder's constant banner from `decoy_loopback.py`,
then the decoy counts what arrives into one scratch buffer, zeroed after each
read, up to 4096 bytes or 5 s, and closes. Nothing received is stored,
logged or forwarded. Only IPv4 is bound.

**Bounds.** One thread and one selector (the unit has `TasksMax=16`). At most
8 open connections; at most 30 served connections per rolling minute (the
intake's own decoy rate, a test keeps them equal); 5 s per connection.
A connection over a bound is accepted and closed at once, unanswered and
unreported, and only counted (`dropped_busy`, `dropped_rate`). An accept
error (`EMFILE`, ...) is counted and rests the listeners for 0.1 s, so a
repeated one is not a busy loop.

**What it reports.** Each served connection becomes P2's closed event
(`decoy_report.interaction_from_observation`), sent as one line to
`/var/lib/azazel/run/decoy-intake/decoy-intake.sock` by `decoy_sender.py`.
The send **never waits**: the socket is non-blocking, so an intake whose
backlog is full refuses the connect at once, and a line that does not fit at
once is not sent. (The first revision waited up to 0.5 s, during which the
accept loop stood still; review of #272. A test measures accept-to-banner
latency while every report goes to a stuck intake.) Nothing is read back. If
the intake is absent, full or slow, or the report fails in any other way,
the interaction is dropped and counted (`send_failed`); the decoy keeps
serving. The peer address `accept` returns is discarded at the call;
the event has no field for it (§7 Q8); the log carries only ports and
counts.

**The runtime boundary, and the one connect.** The listener rule of §7 Q7
(`decoy_listener.py` may bind and listen, never connect) is unchanged. The
report needs one `AF_UNIX` connect, which the listener rule forbids. Rather
than loosen that rule, `tests/unit/test_runtime_boundary.py` now applies it
to **every** module the decoy process loads: the six runtime files of
`DECOY_PROCESS` (the import closure of `decoyd.py`) and the library modules
they import (`azazel_nexus`, `boot_id`, `content_store`, `decoy`,
`decoy_interaction`, `decoy_isolation`). A test imports the decoy's module in
a fresh `python -I` and requires exactly these thirteen names, the runtime
package included (`DECOY_IMPORT_CLOSURES`, #276), with one
exception, `DECOY_SENDER = "decoy_sender.py"`, matched by full path. The
sender may name `connect` and nothing else the listener may not; it may not
name an internet or datagram family, `bind`, `listen` or `accept`; its only
family is `AF_UNIX` stream, however the constructor is spelled
(`socket.socket`, `SocketType`, or a name bound by `from socket import
socket as S`), with no keyword; it has exactly one `connect(_PATH)`. `_PATH`
and `DECOY_INTAKE_SOCKET` are each bound **exactly once** in the whole file,
by a module-level `name = value` (`_PATH` from `DECOY_INTAKE_SOCKET`, that
from a literal equal to the layout's decoy-intake socket); every other way
to bind a name counts as a second binding: a tuple target, `for`, `with ...
as`, walrus, `del`, a function argument or its default, `import ... as`,
`except ... as`, `global`/`nonlocal`, a definition, a `match` capture. No
other module of the decoy process may name either. No module of the decoy
process may name `environ`, `getenv`, a process call, `globals`, `locals`,
`vars`, `setattr`, `delattr`, `getattr`, `__import__`, `eval`, `exec`,
`compile`, `importlib`, a function's or module's internals (`__globals__`,
`__dict__`, `__defaults__`, ...), a name resolver (`getaddrinfo`,
`gethostbyname`, `gethostbyname_ex`, `gethostbyaddr`) or `create_server`,
as an attribute, an imported name or a bare name.

These are AST rules, and what they establish is that **each listed mutation
is caught**, not that no other spelling exists: forty-one mutations of the
real files, twenty-one from the first revision (an internet or datagram
family, another path, a second connect, `sendto`, an environment read, a new
import of an egress module, a connect in the listener or the daemon) and
twenty for the review of #272 (the path bound by a default argument, a tuple,
a walrus, `for`, `with`, `except`, `import as`, an annotation, `del`,
`globals()[...]`, `vars()[...]`, `setattr`; the constructor by name with
integer or single arguments or a keyword; `getaddrinfo`, `gethostbyname`,
`create_server`; the daemon setting the sender's path; `getattr` in the
namespace check), and a same-named sender in a subpackage. The systemd
sandbox (`RestrictAddressFamilies=`, `IPAddressDeny=any`) is the barrier
that does not depend on spelling. The sender has no `AF_INET` exemption: it
gains nothing from `EGRESS_EXEMPT` or `LISTENER_EXEMPT`.

`decoy_listener.open_namespace_listener` sets one socket option,
`SO_REUSEADDR`, so that a restart is not refused while a closed connection is
in `TIME_WAIT`; the P1 test that read the listener's calls now allows exactly
that one. The functional-readiness row stays `loopback-only`: its test now
allows exactly one importer of the listener, `decoyd.py`, whose unit is never
granted.

**Deferred:** the decoy's `ExecStartPre=` probe rerun (done in §14, in
process, as the check of the helper's isolation record); the catalogue and the
commissioned prefix reaching the decoy (and then binding the catalogued
address, `open_listener`, instead of the namespace wildcard); IPv6; the
`IPAddressAllow=` question of §10. A loopback run in a container is not VM
or hardware evidence; `HG-06` and the decoy-sandbox gate stay open.

## 13. The namespace unit's and the helper's bodies as implemented

The bodies deferred in §10. `az-decoy-nsd` and `az-decoy-netd` now build the
decoy network and take it down. Like the decoy (§12) they still **admit
nothing**: the `DECEPTION_EXPOSURE` tier is withheld as
`isolation_evidence_absent` on every pass, no policy can name the three
units, and the installer installs, preset-disables and masks them. The
isolation evidence producer is the next phase.

**Who does what, and why the namespace unit needs `CAP_NET_ADMIN`.** Every
act inside the decoy namespace (`lo` up, an address, a route) needs
`CAP_NET_ADMIN` in that namespace, and reaching the inside (`ip -n`) needs
`setns`, so `CAP_SYS_ADMIN`. The helper has no `setns`; the namespace unit
had no `CAP_NET_ADMIN`. So with the privileges of §10 nobody could configure
the inside. Checked in a privileged container (`setpriv --bounding-set`;
a mechanism check, not VM or hardware evidence): with `CAP_SYS_ADMIN` alone,
`ip netns add` succeeds, and `ip -n <ns> link set lo up` and creating the veth
pair are refused (`RTNETLINK answers: Operation not permitted`); with
`CAP_SYS_ADMIN` and `CAP_NET_ADMIN` both succeed. The namespace unit
therefore holds exactly `CAP_SYS_ADMIN CAP_NET_ADMIN`. That adds nothing real:
a compromised body of that unit is host root already (§10). `ip -n` also
makes a private mount namespace for itself after `setns` (strace:
`setns(CLONE_NEWNET)`, `unshare(CLONE_NEWNS)`, a slave remount of `/`, a fresh
`/sys`), so its `RestrictNamespaces=` is `net mnt`. Both are pinned exactly in
`ServiceProfile`; `CAP_SYS_ADMIN` is still this unit's alone, and
`CAP_NET_ADMIN` is held by this unit and the helper and by no other.

| | `azazel-decoy-nsd.service` (`NAMESPACE_STEPS`) | `azazel-decoy-netd.service` (`HELPER_STEPS`) |
| --- | --- | --- |
| where | host namespace, and the decoy namespace through `ip -n` | host namespace only; never enters the decoy's |
| checks first | none: `ip netns add` and the veth pair each refuse to replace an existing one | `ip link show dev az-decoy0` and `nft list table inet azazel_decoy` must both **fail** (find nothing); if either finds something, it exits 1 having changed nothing |
| start | 1. `ip netns add azazel-decoy`; 2. `ip link add name az-decoy-host0 type veth peer name az-decoy-ns0 netns azazel-decoy` (the decoy's end is created inside; `netns NAME` opens the handle, no `setns`); 3. `ip -n azazel-decoy link set dev lo up`; 4. `… address add 10.255.196.2/30 dev az-decoy-ns0`; 5. `… link set dev az-decoy-ns0 up`; 6. `… route add default via 10.255.196.1 dev az-decoy-ns0` | 1. `nft <NFT_RULESET>` (the rules first, one transaction, which `create table` makes fail if the table exists); 2. `ip link add name az-decoy0 type bridge`; 3. `ip address add 10.255.196.1/30 dev az-decoy0`; 4. `ip link set dev az-decoy-host0 master az-decoy0`; 5. `ip link set dev az-decoy0 up`; 6. `ip link set dev az-decoy-host0 up` |
| `ExecStop=… stop` | `ip link delete az-decoy-host0` (the pair goes with it), then `ip netns delete azazel-decoy` | `ip link set dev az-decoy-host0 down`, `ip link delete az-decoy0`, then `nft delete table inet azazel_decoy`: the path is cut before the rules go, and if cutting it fails the table stays (exit 1) |

The full paths are `/usr/bin/ip` (the file iproute2 installs on Debian 13;
`/usr/sbin/ip` links to it) and `/usr/sbin/nft`. The decoy's end is
`decoy_netns.DECOY_VETH` (`az-decoy-ns0`), imported from the decoy's own
check (§12), so the two cannot differ; the host's end is `az-decoy-host0`;
both fit `IFNAMSIZ`. The /30 has two hosts, the bridge (`.1`) and the decoy
(`.2`). `azazel_nexus.decoy` still has no default bridge prefix; the
commissioned prefix replaces this fixed one when §7 Q9 reaches the units.

**Order, and nobody waits.** Namespace unit, then helper, then decoy, as
declared in §10. The helper needs the host end of the pair, and the namespace
unit made it before it exited, so nothing polls for a link. Letting the
helper create the pair and the namespace unit configure the inside afterwards
would need the namespace unit to run after the helper (the declared chain
reversed) or to wait for it (the unit with `CAP_SYS_ADMIN` kept running, and
a one-shot that waits for a unit ordered after it never finishes). The
decoy's start-time check cannot wait usefully either: it has no capability to
configure what it finds. The namespace unit runs six short commands and exits.

**Not chosen: systemd holding the namespace** (`PrivateNetwork=yes` with
`JoinsNamespaceOf=`, §10). It removes `CAP_SYS_ADMIN`, but the host side
(bridge, the host end, host rules) still needs a `CAP_NET_ADMIN` process in
the host namespace and the inside needs one in the decoy's, so it would be two
`CAP_NET_ADMIN` units in place of one unit holding both; there would be no
`/run/netns/azazel-decoy`, which the decoy's own namespace check (§12) compares
against; and its ordering and lifetime are not VM-checked. Not clearly
simpler, so option (a) stays.

**How a command is run** (`runtime/src/azazel_nexus_runtime/decoy_network.py`).
`os.posix_spawn` of an argument tuple that is one of the module's constants
(`run_fixed` refuses any other, before a process is made; the set is exactly
the goldens of the tests), with an empty environment and `SIGPIPE` reset to
its default in the child (`setsigdef`); no shell, nothing read back, the
program's output goes to the unit's journal stream. `posix_spawn` needs no
pipe, which matters: the namespace unit's filter denies `@ipc`, which holds
`pipe` and `pipe2`, and `subprocess` opens one for every child. Each command
has 2 s (`STEP_SECONDS`), then `SIGKILL`; the longest start (checks, every
step, every undo) is thus well inside `TimeoutStartSec=30s` (a test checks
it), so systemd never kills a start half-undone. Neither executable reads an
argument (other than the single word `stop`, from its own `ExecStop=`), a
file, the environment or a socket. `decoy_network` is the only module of the
distribution that names `posix_spawn`, and only the two executables import it
(`tests/unit/test_runtime_boundary.py`; no module on the model acquisition
path may import it either). The names and addresses live in the leaf
`decoy_addresses.py`, which imports nothing; the unit renderer
(`hardening.py`) takes the decoy subnet from there and never loads the module
that starts processes (a test checks it).

**Fail closed.** The helper changes nothing that is already there: if the
bridge or the table exists (a crash, a second start), it exits 1 before its
first step. The two checks print the expected `ip`/`nft` "does not exist"
errors to the journal on every normal start; the line before them says so.
The table is also never replaced: its ruleset begins with `create table`,
which fails if one exists, and the whole transaction is then refused (so
nothing races the check). A step that fails or cannot be started stops the
start: the undo commands of the steps already done run in reverse, and the
executable exits 1 with the number of failed undos (systemd runs no
`ExecStop=` after a failed one-shot start, so the body cleans up after
itself). A step that **timed out** may have half-made its object, so its own
undo runs as well; a step that failed outright made nothing, and may have
failed because the object already existed, which is not its to remove.
`stop` runs every undo in reverse and exits 1 if any failed. **The table is
a guard:** its undo runs only if every undo after it succeeded, at start and
at stop, so while the bridge or the host end may still be there the rules
stay (review of #273; before, a failed bridge deletion was followed by the
table's). The namespace unit has no guard: deleting the namespace takes the
pair with it. Leftovers of a crash make the next start of the namespace unit
fail at its first step, which then removes only what it made itself.

**The rules** (`NFT_RULESET`, a golden in the tests). One `inet` table,
`azazel_decoy`, made with `create table`, so an existing table of that name
is never replaced or added to. Chains on the `forward`, `input` and
`output` hooks with `policy accept`: this table only ever drops (an accept
here never overrides another table's drop), so it adds isolation and opens
nothing.

- forward, toward the decoy: TCP from a source in the set `approved_v4` to
  `10.255.196.2`, ports 2222, 2323 and 8080 (`decoyd.SERVED`; a test keeps
  them equal), accepted; everything else out of `az-decoy0` dropped;
- forward, from the decoy: only established replies from those ports to an
  approved peer; everything else in from `az-decoy0` dropped. The decoy's
  report to the intake goes over a Unix socket, so no outbound network path
  is needed;
- input: everything from `az-decoy0` to the host dropped (management,
  control plane, every host service);
- output: everything from the host to `az-decoy0` dropped.

**`approved_v4` is empty, and nothing in this build adds to it.** Until the
commissioned scope arrives (§7 Q9), every packet to and from the decoy is
dropped, so even a granted tier would not be reachable from outside. The set
is the frame Q9 fills.

**The decoy's `IPAddressAllow=`.** A VM run of the real decoy unit (Debian 13,
systemd 257.13, `main` 454955e, with only the marker and controller
dependencies removed; a mechanism check, not hardware evidence) showed that
`IPAddressDeny=any` alone also drops what the decoy receives: a connect from
inside the namespace timed out, and with an allowance the banner came back.
The decoy profile therefore states `IPAddressAllow=10.255.196.0/30`
(`decoy_addresses.DECOY_SUBNET`), statically because #253 refuses drop-ins, and
keeps `IPAddressDeny=any`. Not `localhost`, which helped only the test.
`ServiceProfile` requires exactly that one allowance on the decoy. The filter
matches the peer's address, so a peer outside the /30 is denied by the unit as
well as by the table; prefixes Q9 approves will have to be added here too.

**Fallback tunnel devices.** A kernel with tunnel modules loaded (`sit`,
`ipip`, `ip_gre`, ...) creates their fallback devices (`sit0`, `tunl0`, ...)
in every new namespace unless `net.core.fb_tunnels_only_for_init_net` says
otherwise, and the decoy then refuses to start (§12). The namespace unit does
**not** change that sysctl and does not delete such devices: deleting them
would mean reading which exist (nothing is read back here) or a list of names
that varies by kernel. A refusal of the decoy is the fail-closed outcome. On
Debian 13 by default the new namespace holds `lo` alone (VM-checked); in the
container run below, once a `sit` device had loaded the module, `sit0` did
appear in the namespace, which is exactly the case the decoy refuses. The
operator's setting is in
[operations](operations.md#deception-lite-decoy-network-196) (value `2`).

**m2, the helper's further sandbox** (review of #268): `ProtectClock=yes`,
`ProtectHostname=yes`, `ProtectKernelLogs=yes`, `RestrictRealtime=yes`, and
`InaccessiblePaths=-/run/dbus/system_bus_socket` and `-/run/systemd/private`
(a second barrier behind `AF_NETLINK`), with `ExecStop=`, pinned whole as
`DECOY_HELPER_SANDBOX`. A narrower `SystemCallFilter=` for the helper is not
in this change; the shared `@system-service` stays, and narrowing it is a VM
item. `ExecStop=`, `ExecStopPost=`, `ExecStartPost=` and `ExecReload=` are
now reserved keys: only the two pinned extras name one.

**Tests** (`tests/unit/test_decoy_network_body.py`, with the profile tests
updated). A fake executor records every command: the exact command lists of
both units as goldens, in order; the exact ruleset as a golden; a failure at

the helper with `CAP_NET_ADMIN` alone loaded the table and attached the host

## 14. Isolation evidence

The "isolation check" of §5 D1, deferred in §10 and §13. After the helper has
built the host side of the decoy network it reads it back, and writes **this
boot's record** of fixed results; the decoy refuses to listen without one
that passed. The `DECEPTION_EXPOSURE` tier is still withheld on every pass,
for the reason in "Why the pass still withholds" below.

### The constraint, and the choice

§5 D1 says the activation pass consumes "only fresh evidence from this boot".
That cannot hold: the pass runs before the three units (they carry its grant
markers, §10), and the evidence describes a network that only exists after
they have run. Within one boot the pass can never see isolation evidence for
that boot, and §5 did not say what to do about it. The candidates:

| | idea | verdict |
| --- | --- | --- |
| A | the helper checks what it built, right after building it, and writes a boot-bound record; the decoy requires a passing record before it listens | **chosen** |
| B | the next boot's pass grants on the previous boot's record | **not chosen**: a previous boot's network says nothing about this boot's (kernel, modules, sysctls, other tables may differ); it needs a record that outlives `/run`, so persistent root-written state; and it grants exactly when the record is stale |
| A + B | both | B adds the weakness above to A and nothing A lacks in the boot that exposes |

A is the smaller and the safer: it holds on **every** start, whatever the
pass decided, it needs no state beyond the boot, and it does not touch the
grant path. It is also what the tier will need once it may be granted: the
grant and the per-start check are two different conditions (§5 already asked
for both, the pass's and the decoy's `ExecStartPre=` rerun), and this is the
second one.

### What is checked

Two fixed commands, added to `decoy_network`'s fixed set and the only ones
whose output is read (`HELPER_VERIFY`, run by `capture_fixed`):
`nft list table inet azazel_decoy` (the same argument list as the helper's
second "absent" check) and `ip -j -d address show`. The checks
(`azazel_nexus.decoy_isolation.CHECKS`, evaluated by
`decoy_isolation_check.evaluate`):

| check | holds when |
| --- | --- |
| `nft_table` | the listed table, without indentation and blank lines, is exactly the ruleset the helper loads (container-checked listing of nftables 1.1.3, Debian 13) |
| `approved_v4_empty` | the set `approved_v4` is listed with no element |
| `bridge` | exactly one `az-decoy0`, kind bridge, up, attached to nothing |
| `bridge_address` | its only IPv4 address is `10.255.196.1/30`; IPv6 only link-local |
| `bridge_ports` | the only link attached to it is `az-decoy-host0` |
| `host_veth` | `az-decoy-host0` is a veth, up, attached to the bridge, its peer in another namespace (`link_netnsid`), no IPv4 address |
| `decoy_veth_off_host` | no `az-decoy-ns0` in the host namespace |
| `subnet_exclusive` | no other host link holds an address in `10.255.196.0/30` |

Each is `pass`, `fail` or `unreadable` (the command failed, was killed, or
printed something that cannot be read; never a pass). Another nftables
release that prints the same rules differently reads as `fail`, which keeps
the decoy refused: a listing the code does not recognise is not one it may
vouch for (operations says so).

**What is not in it.** The decoy namespace's own interfaces: only a process
inside the namespace can list them, and the helper cannot enter it (`setns`
needs `CAP_SYS_ADMIN`; the namespace unit, which can, runs before the helper
and its filter denies pipes). The decoy checks them itself, from inside, at
start and before every bind (§12). **No packet is sent:** this reads the
configuration, it does not test the denied paths with traffic; `HG-06` stays
the gate for that. And it is a reading at one moment: a root process that
changes the table afterwards is not seen until the next start.

**Limits of the checks as written** (review of #274):

- `nft_table` is an exact match of nftables' text listing, so it depends on
  the nftables release: a release that prints the same rules differently
  fails closed. Comparing the structure of `nft -j list table` instead would
  remove that dependence; it is a later change (another fixed argument list
  and a JSON comparison), not done here.
- `host_veth` checks that the host end's peer is in **another** namespace
  (`link_netnsid`), not that it is the decoy's: mapping the id to
  `/run/netns/azazel-decoy` would need a further command. The decoy's own
  check (§12) covers the other side: it runs only in that namespace, with only
  `lo` and `az-decoy-ns0`.
- `subnet_exclusive` looks at IPv4 addresses only; the decoy network has no
  IPv6 prefix, and the bridge's IPv6 is limited to link-local by
  `bridge_address`.

**Errors are failures.** A listing missing a key `ip -j` always prints
(`ifname`, `flags`, `addr_info`) or holding another type there makes every
check that reads it `unreadable`; an exception while reading back or
recording (a missing key, an I/O error, anything) makes the helper undo the
whole build and exit 1, and an error inside the read-back kills and reaps the
command first (review of #274; tests for each).

**What the helper's journal says on failure**, one line per stage, so a
failure can be placed: `check <i> of 2: already present; nothing was
changed` (a bridge or table left behind), `step <n> of 6 failed (<status>);
undoing` (a build step, for example `ip` exiting 2 on `File exists`),
`isolation check: <check> pass|fail|unreadable, ...` followed by `the
isolation check did not pass or was not recorded; undoing`, or `the isolation
check failed with an error; undoing`.

### The record

```
{"boot_id":"<this boot>","checked_at":"YYYY-MM-DDTHH:MM:SSZ",
 "checks":{"<check>":"pass"|"fail"|"unreadable", ...},
 "contract":"azazel-nexus/decoy-isolation/v1"}
```

One line, keys sorted, no spaces, ASCII, a newline (`render_evidence`). A
reader (`parse_evidence`) refuses anything that does not render back to the
same bytes, so another key, a missing one, a reordered or duplicated key, an
escape, whitespace or a value outside the fixed set are all refused. At most
4096 bytes. No address, interface name, command output or secret.

**Where and whose.** `/run/azazel-decoy-isolation/isolation.json`. The
directory is the helper's `RuntimeDirectory=` (root, `0755`), so systemd makes
it when the helper starts and removes it when the helper stops; `/run` is
cleared at every kernel boot. `ServiceProfile` pins it as the helper's only
writable place and refuses it as any other unit's runtime directory; `0755`
is the one exception to the `0750` of runtime directories, because the decoy
reads the record under its own account.

**The writer** (`decoy_isolation_check.Recorder`, used by `az-decoy-netd`
only; it starts no process and never imports `decoy_network`):

1. before any check or step, removes a previous record and a leftover
   temporary file (never through a link) and reads this boot's id the
   protected way (`edge_package.read_current_boot_id`); failing either, it
   changes nothing and exits 1;
2. after the build, writes the record under a fixed temporary name
   (`O_CREAT | O_EXCL | O_NOFOLLOW`) in the directory opened with
   `O_NOFOLLOW` and checked to be root's and writable by nobody else, makes
   it `0644` (the unit's `UMask=0027` would leave it unreadable to the decoy),
   syncs it and renames it over the fixed name;
3. unless every check passed and the record was written, the helper undoes
   the whole build and exits 1, and the decoy's start fails as a dependency;
4. at stop, the record goes first, then the network.

Two read-back commands keep the longest start within `TimeoutStartSec=30s`
(two absence checks, six steps, two read-backs, three undos at 2 s each; a
test keeps the sum). Only the helper opens a pipe; the namespace unit runs
with no file action and its filter still denies `@ipc`.

**The reader** (`azazel_nexus.decoy_isolation`, in the library so that a
later pass reads with the same code): the directory and the file are opened
with `O_NOFOLLOW`, both must be owned by root and writable by nobody else,
the file a regular one within the limit. The decoy
(`require_isolation_for_decoy`, called by `az-decoyd` after its namespace
check and before any socket) also requires the record's boot id to be this
boot's, its time not in the future (5 s skew) and every check `pass`. There
is no maximum age: the helper runs once per boot, the decoy `Requires=` it,
and the record goes away with it. Its refusals are fixed phrases with fixed
check names, never content. Nothing (argument, file, environment variable,
flag) skips it. The reader is in the library and reads the boot id through
the leaf `boot_id`, as `edge_package` does (#276; through `edge_package`
before, which brought about forty library modules into the decoy and the
helper). The decoy's import closure is the thirteen modules of §12, and
§12's boundary rules apply to each of them.

### Why the pass still withholds

`ActivationController._withholding_reason` still returns
`isolation_evidence_absent` for the tier, unconditionally, and `activate`
still takes no evidence. The producer frame exists
(`installed_isolation_reading`, which reads the fixed record and answers
`absent`, `refused`, `not_this_boot`, `not_passed` or `passed`), but nothing
calls it from the pass, for three reasons:

- at the pass this boot's record cannot exist (above), so consuming it would
  only ever withhold, and consuming a previous boot's is B, not chosen;
- granting the tier needs things this change does not have: the approved
  prefixes (§7 Q9; `approved_v4` is empty, so even a granted decoy is
  unreachable), the exposure units in the measured generation (§10), the
  `HG-06` and decoy-sandbox hardware gates (§7 Q10);
- the grant condition for the tier is then a decision of its own: what the
  pass requires before it may write the three markers, with this record as
  the per-start condition behind it. That change is made deliberately in
  `_withholding_reason`, with tests, never through a flag.

A test keeps it so: with a passing record in place the three units are still
withheld as `isolation_evidence_absent`, nothing in the controller takes a
reading, and nothing in the runtime calls the frame. The tripwire of §10 is
unchanged.

**Not done here:** granting the tier (its condition, the measured unit
files, approved prefixes, `HG-06` and the decoy-sandbox gate); a packet test
of the denied paths; IPv6; a check of the namespace's interfaces by anyone
but the decoy; the structural `nft -j` comparison above. Two more, from the
review of #274:

- **Reading the table back on every decoy restart.** The record is taken
  once, when the helper starts; a decoy restarted later in the boot accepts
  it without a fresh look, so a table changed in between is not seen. A
  fresh read-back per decoy start needs a privileged step at each start (the
  decoy has no capability and no host view), for example the helper re-run
  as the decoy's dependency, and is left for the phase that grants the tier.
- **A clock that moves backwards.** The decoy refuses a record dated more
  than 5 s after its own clock. A node that boots with a real-time clock
  ahead of the true time, writes the record, and is then corrected backwards
  by time synchronisation keeps refusing the decoy until the helper is
  restarted (or the clock passes the record's time again). That fails
  closed, so it is an availability problem, not an exposure; a monotonic or
  boot-relative stamp would avoid it.

The grant phase is designed in [granting the exposure tier](deception-exposure-grant.md) (decided 2026-10-22: all recommended defaults).
