# HG-06 — actively test decoy isolation

Owner: [#4](https://github.com/01rabbit/Azazel-Nexus/issues/4), explicit child
work; dedicated child issue number unassigned.
Status: **not run; hardware-unverified**.

Use the [campaign](../hil-campaign.md) authorisations, console and isolated
controlled test network, [confidentiality rules](../inventory-confidentiality.md)
and [evidence lifecycle](../hil-evidence-records.md). This checks actual denied
traffic from a real decoy namespace on the declared bridge/kernel/firewall.
A ruleset dump or failed connection alone does not prove isolation.

1. Keep redirects and exposure withdrawn. Verify the declared profile, assets,
   commissioning and trust allow the candidate decoy at all; if not, record
   ineligibility/`not-run`, never a passed isolation exercise.
2. Attach the real test container only to `az-decoy0`. Record protected topology
   and approved generation. Use controlled responders representing protected,
   management, control-plane and Internet zones, all inside the authorised lab.
   Do not target production systems or the actual public Internet.
3. Confirm each responder is healthy/reachable through an independent permitted
   control path and instrument its ingress plus the decoy-side attempted traffic.
   A dead responder or broken source route is inconclusive. Do not open a denied
   route as a positive control. Declare protocols, address families, destinations
   and bounded attempts; missing coverage remains explicitly untested.
4. From **inside the decoy namespace**, attempt each declared denied connection
   to each required zone. Correlate source attempts with kernel/firewall drop
   observations and independent destination capture. Record failures, timeouts,
   unexpected arrivals and capture health, using sanitised zone labels/HMAC
   references rather than addresses or hostnames. Incomplete/dropped captures
   or an unobserved attempt cannot prove denial.
5. Re-run on every boot and immediately before each proposed exposure. Record
   boot/run, timestamp, generation, tested path/zone, method and result. An old
   successful check is not current eligibility. Do not expose merely because
   this runbook completed; all activation/redirect gates still apply.
6. Sanitise, attest and validate the HG-06 record with the HIL gate validator
   **added in this change**, per [tools](../hil-evidence-records.md#tools-and-trust).

Any successful denied path or missing check immediately withdraws redirect
eligibility. Remove exposure first, stop/quarantine the decoy through the
approved controller, verify isolation from the console, and retain the failure.
If cleanup is uncertain, keep the test links physically isolated. Repair via a
reviewed generation and repeat the full check; a retest does not erase failure.
This proves only the exercised paths/protocols on this tuple, not every escape
or future firewall state. It grants no enforcement authority.
